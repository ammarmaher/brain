# Rate limiting and query budgeting

Meta Content Library and API both have limits at the individual researcher level that:

- Put a cap on the number of queries allowed per user per minute (a separate limit for each tool). This is called a _rate limit_.

- Put a cap on the number of retrieved data records (posts, for example) per user per seven-day rolling window. This limit, called a _query budget_, is shared between the two tools per user. In other words, a single researcher has a total query budget between the two tools, regardless if they are using just Content Library, just Content Library API, or both.


Maintaining a rate-limiting and query-budgeting policy ensures that the tools run efficiently and provide all users with consistent data access, unhindered by reduced performance. It also provides a measure of protection against system flooding.

## What are the limits?

### Rate limits for Content Library

- 60 queries over any one-minute interval

### Rate limits for Content Library API

- Synchronous search queries: 60 queries over any one-minute interval

- Asynchronous search queries: 1 query per minute


See [Search guide](https://developers.facebook.com/docs/content-library-api/guide-search-object) for information about the difference between synchronous and asynchronous searches.

### Combined query budget per researcher

For Content Library and API combined, you can
retrieve a maximum of 500,000 data records per seven-day rolling window. You have a maximum query budget of 500,000 comment data records per seven-day rolling window. The rolling window is one week previous to the current timestamp (to the second). If you are blocked by hitting the query budget, you should not need to wait long before you try again.

If you are using the Content Library API in a third-party cleanroom environment, and if that environment supports including multimedia in posts, there is an additional query budget of 1000 queries with multimedia per rolling week.

## How to request a limit increase

If you have questions or concerns about the impact of your limits on your research, contact us through [Direct Support](https://developers.facebook.com/docs/content-library-and-api/direct-support).

## Tips for staying below the limits

In general, searching for common words and requesting to fetch all the results can exhaust your query budget. Consider narrowing your searches for more targeted results.

### Get your current usage

Use the `budgets` endpoint to check your maximum number of data records retrieved per rolling 7-day period (query budget) and how much of that budget you have already used

RPython

```r
library(reticulate)
client <- import("metacontentlibraryapi")$MetaContentLibraryAPIClient

client$set_default_version(client$LATEST_VERSION)

response <- client$get(path="budgets")

jsonlite::fromJSON(response$text, flatten = TRUE)
```

```py
from metacontentlibraryapi import MetaContentLibraryAPIClient as client

client.set_default_version(client.LATEST_VERSION)

response = client.get(path="budgets")
display(response.json())
```

This is a sample of the output:

```python

{'timestamp': 'Wednesday, October 29, 2025 06:04:28 PM GMT',
  'queries': {
         'current_usage': 246000,
         'preallocated_rows_for_running_queries': 0,
         'total_usage': 246000,
         'max_usage_limit': 500000
  },
  'comments': {
        'current_usage': 1000,
         'preallocated_rows_for_running_queries': 0,
         'total_usage': 1000,
         'max_usage_limit': 500000},
 'multimedia': {
         'total_usage': 0,
          'max_usage_limit': 1000}
}
```

- _queries.current\_usage_ is the number of results already returned by completed queries in the current 7-day rolling time window as of the current timestamp.

- _queries.preallocated\_rows\_for\_running\_queries_ is the number of results (rows) allocated for asynchronous queries that are in progress.

- _queries.total\_usage_ is the sum of _current\_usage_ and _preallocated\_rows\_for\_running\_queries_.

- _queries.max\_usage\_limit_ is the maximum number of queries allowed in a 7-day rolling window.

- _queries.timestamp_ marks the point in time at which these statistics were collected.


#### Current usage for comments

If you are using the Meta Content Library API to also fetch comments, comment-specific query budget is also available as comments JSON object with the following fields:

- _comments.current\_usage_ is the number of comment results already returned by completed queries in the current 7-day rolling time window as of the current timestamp.
- _comments.preallocated\_rows\_for\_running\_queries_ is the number of comment results (rows) allocated for asynchronous queries that are in progress.
- _comments.total\_usage_ is the sum of current\_usage and preallocated\_rows\_for\_running\_queries.
- _comments.max\_usage\_limit_ is the maximum number of queries allowed in a 7-day rolling window.

#### Current usage for multimedia

If you are using the Meta Content Library API in an approved third-party cleanroom environment (as opposed to Meta's Secure Research Environment), _and if that environment supports including multimedia in posts_, multimedia-specific query budget usage is also available as a `multimedia` JSON object with the following fields:

- _multimedia.total\_usage_ is the number of calls with multimedia in the current 7-day rolling time window as of the current timestamp.

- _multimedia.max\_usage\_limit_ is the maximum number of calls with media allowed in a 7-day rolling window.


The query budget specific to queries containing multimedia is 1000 queries per 7-day rolling window.

### Estimate response size for asynchronous queries

Use the `/estimate` resource in search to get a rough idea of how much data would be returned from an asynchronous search that you plan to run. See [Estimating response size](https://developers.facebook.com/docs/content-library-api/guide-search-object#estimate) and [Asynchrounous search](https://developers.facebook.com/docs/content-library-api/guide-search-object#async-search) in the _Search Guide_ for more information on these topics.

**Points to keep in mind**:

- The API can only return up to 100,000 results from a single asynchronous query, so it can be helpful to know in advance if your query is likely to fail because the response size is too large.

- The query budget of 500,000 results in a rolling seven-day window can be used up quickly on just a few queries with high predicted results.


If the estimate comes out higher than 100,000, you might consider modifying the parameters to reduce the response size. You can continue to modify the search parameters and get new estimates until the search results are predicted to fall below the maximum allowed or close to the response size you prefer.

This is typically most useful for post searches or comments fetching because the number of results tend to be higher, but it can be used to estimate the number of results that would be returned by any query.

RPython

```r
library(reticulate)
client <- import("metacontentlibraryapi")$MetaContentLibraryAPIClient

client$set_default_version(client$LATEST_VERSION)

# Request an estimate:
response <- client$get(
            path="facebook/posts/estimate",
            params=list("q"="dogs")
)

# Display the estimate
jsonlite::fromJSON(response$text, flatten = TRUE)
```

```py
from metacontentlibraryapi import MetaContentLibraryAPIClient as client

client.set_default_version(client.LATEST_VERSION)

# Request an estimate:
response = client.get(
          path="facebook/posts/estimate",
          params={"q": "dogs"}
)

# Display the estimate:
display(response.json())
```

library(reticulate)
client <- import("metacontentlibraryapi")$MetaContentLibraryAPIClient

client$set_default_version(client$LATEST_VERSION)
