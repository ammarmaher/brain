GAP A·ValidateAccountName·10

09Gap A — Account Name Uniqueness

The playbook requires an async backend call. The wizard does a client-side scan of the cached tree. The two look identical to a casual screenshot reviewer — but they have very different failure modes.

What the brain says

From [BRAIN-OUT] Add Client/07-VALIDATIONS.md § Async checks:
GET /api/Node/ValidateAccountName?AccountName= → returns bool. Step 1. Debounce 300ms + cancel-on-input. Map true (exists) to a custom accountNameTaken validator error.

What the code does

// [CODE] client-information-step.component.ts:84-95
protected readonly accountNameError = computed<ValidationMessage | null>(() => {
  const v = this.value().accountName;
  const sync = accountNameValidator(makeControl(v));
  if (sync) { /* sync rules */ return messageFor(sync) ?? null; }
  const root = this.state.treeRoot();
  if (!root) return null;
  // ⚠️ This is a CLIENT-SIDE scan against the locally-cached tree.
  // It does NOT call /api/Node/ValidateAccountName.
  const taken = collectAccountNames(root).includes(v.trim().toLowerCase());
  return taken ? { key: 'hierarchy.validation.duplicateAccountName' } : null;
});

Case-only differenceLowercase compare — OK if backend agreesBackend authoritative
Recently deleted then re-addedStale cache → false negativeBackend always current

12Gap D — Username Uniqueness

Identity Service exposes POST /api/user/exist. The Step 5 component imports the username-unique validator pipeline. Yet the wire-in is a stub: userNameUniqueValidator(() => of(false), ...) — hardcoded "never taken".

Direct quote from the code

// [CODE] client-account-owner-step.component.ts:53-54
/*** No backend wired yet on the Add-Client owner step — reserved-set only via FALCON_RESERVED_USERNAMES. ***/
private readonly usernameUniqueFn = userNameUniqueValidator(() => of(false), FALCON_RESERVED_USERNAMES);

The comment is honest. Whoever wrote this knew the wire was missing — it was queued for "later". Later didn't happen.

Why this is severe

RiskSeverity
Two operators create same username concurrently → server-side DuplicateUsername (409) at submitHIGH — race condition

The fix

  FALCON_RESERVED_USERNAMES,

// The pipeline is already debounced/cancelled-on-input inside userNameUniqueValidator,
// so only the loader function needs to change. ~5-line edit.

15The Decision Tree I Didn't Walk

Standing rule feedback_falcon_custom_library_mandatory § 3 lays out a strict 8-step customization order. R2's agent walked steps 1–4 for some components and skipped to step 8 ("raw page implementation") for the row table. v2 walks the full tree for Steps 3+4.

The right answer

<falcon-angular-data-table> exists. It supports column config + per-cell ng-template via falconDataTableCell directive. So Step 2 of the tree (existing Falcon ng-template support) is the right landing zone — not Step 7 (feature-local wrapper).

Why R2 short-cut it: the row table already existed when R2's agent inherited the work. The brief said "submit unblocking". The wrapper compiled green. The agent (correctly under its scope) did not refactor it. The orchestrator (incorrectly) accepted that as final.

Orchestrator self-critique: "Falcon library first" is not just a rule about which component, it's a rule about which step of the tree. The orchestrator never asked the agent to walk the tree — only to fix the submit. That was efficient for the bug, inefficient for the doctrine.

23API Wiring — Detailed Sequence

The four missing endpoints share a common reactive pattern. Below: the canonical recipe each integration follows, so any agent picking up the work can apply it uniformly.

The canonical reactive validator recipe
// 1. Inject the relevant service
private readonly api = inject(WhicheverService);

// 2. Wrap the async loader so it returns the validator-error shape Falcon expects
private readonly asyncCheck: AsyncValidatorFn = (control) =>
  toObservable(control.value).pipe(
    debounceTime(300),
    distinctUntilChanged(),
    switchMap(value => this.api.validate(value).pipe(
      map(r => r?.exists ? { resourceTaken: true } : null),
      catchError(() => of(null))   // network errors do NOT block submit
    ))
  );

// 3. Hook the validator into the FormControl
this.form.controls.fieldName.addAsyncValidators(this.asyncCheck);

// 4. Surface the error in the template by reading control.errors?.resourceTaken
