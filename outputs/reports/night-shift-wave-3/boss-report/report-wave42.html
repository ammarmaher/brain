WAVE 4.1 FIX·UNTRACKED() PATTERN·04

03The untracked() Fix

Wave 4.1 bisect: disable the async pipeline → wizard mounts → confirmed culprit. The proper fix is the canonical Angular pattern for "signal writes from RxJS interop context": wrap each .set() in untracked().

The bug

// BEFORE (hung Step 1 mount)
protected readonly accountNameTaken = toSignal(
  toObservable(this.accountNameValue).pipe(
    debounceTime(300),
    switchMap((name) => {
      this.accountNameCheckPending.set(true);   // ⚠️ tracked-context write
      return this.api.checkAccountNameExists(name).pipe(
        finalize(() => this.accountNameCheckPending.set(false)),  // ⚠️ same
      );
    }),
  ),
  { initialValue: false },
);

The fix

// AFTER (mounts cleanly, pipeline emits as expected)
protected readonly accountNameTaken = toSignal(
  toObservable(this.accountNameValue).pipe(
    debounceTime(300),
    switchMap((name) => {
      untracked(() => this.accountNameCheckPending.set(true));   // ✅ explicitly untracked
      return this.api.checkAccountNameExists(name).pipe(
        finalize(() => untracked(() => this.accountNameCheckPending.set(false))),
      );
    }),
  ),
  { initialValue: false },
);

Pattern to remember: Whenever you use toSignal(toObservable(signal).pipe(...)) and the RxJS operators inside the pipe do otherSignal.set(...), wrap each write in untracked(). The toObservable preserves the signal-tracking context into the pipe, so writes that look harmless become tracked-context writes that Angular's cycle detector live-locks on.

05The Residual 422 — Backend-Side

After all the frontend fixes, the create-account POST still returns HTTP 422 InvalidValue. This is the same response the backend has returned across every payload variation across Wave 3, Wave 4, and Wave 4.2. Tried 8+ variations — same generic "Invalid value" message every time. The issue is on the backend.

The diagnostic gap: The 422 body returns {"errorCodes":["InvalidValue"],"errorMessages":["Invalid value"]} with no field path. The .NET JSON deserializer was tested by deliberately sending bad data — it returns a SPECIFIC field path (e.g. "$.info.sector — could not be converted to System.String"). So the 422 is from a downstream FluentValidation or domain rule, not the deserializer. Without backend logs or a specific validator output, the offending field can't be identified from the client side.

Recommended next step (backend-side)

  1. Backend developer pulls the Commerce service logs while we send a fresh request. The 422 path SHOULD log the validator rule that fired.
  2. Once the failing rule is identified, the FE can adapt (add missing field, change format, etc.) OR the BE can adjust the validator if it's overly strict.
  3. Re-run Wave 4.3 verification — same script + the BE-side fix should produce HTTP 201 with the new account in the tree.
