Section 4 — Lessons Learned + Anti-Patterns

Why this chapter exists

In the closing minutes of the Add Client wizard session — after Wave 7 had shipped, after every build was green, after the user had personally verified the entire 5-step flow end-to-end — the user paused and said:

"I need you to make sure that you learn all the things that you made a mistake on, and make sure that you have a good plan and good knowledge."

That sentence is the reason this chapter exists. The other 49 pages of this report describe what we built. This chapter is the durable artifact for how to build better next time. It catalogs every concrete mistake, every anti-pattern that surfaced, and every rule that — if I had followed it on the first iteration — would have saved an hour or three of back-and-forth across the 10+ hour session.

Three audiences read this chapter:

  • Future me — every Ammar session that touches the Add Client wizard, the per-component signals doctrine, or the Falcon dialog component pattern. The rules here turn into pre-flight checks.
  • Other Ammar agents (Auth, Commerce, Core-Gateway, etc.) — most of the anti-patterns surface in any Angular signals + OnPush + Falcon UI codebase. The lessons are portable.
  • The orchestrator (Adnan) — to know which agents to dispatch with what constraints, and which constraints absolutely cannot be ignored ("I will test" being the canonical example).
~30% Estimated fewer iterations had I followed every rule in this chapter on Wave 4

The estimate comes from counting the avoidable retries: M3 (null defaults) took 2 user messages and 2 agent dispatches when 1 of each would have sufficed. M2 + M4 (SAR icon) together added a full additional round-trip — invent the SVG, get rejected, redesign the API. M5 (OnPush row-table) was diagnosed in Wave 6.1 with the wrong fix, surfaced again in Wave 7, and needed a fresh investigation. M11 (Brain SK playbook) pushed Wave 4 forward with the wrong field shape (string for deliveryMethod instead of the canonical int enum) and the wrong assumption about generatePassword timing. Summing the avoidable detours gives roughly 30% — the math is rough, but the lesson is precise: load the playbook, grep the library, respect the constraints.

The 12 Mistakes

Each card below captures one concrete mistake from the session. Severity is calibrated by impact (wasted time + user frustration + risk of recurrence), not by how embarrassing the error was. HIGH means it shipped a wrong-direction iteration that needed full redo; MEDIUM means it cost a user message and a fresh agent dispatch; LOW means it cost a few minutes but did not derail the wave.

M1

Built unit tests when user didn't ask

Severity: low

What happened

During Wave 5.3, I dispatched Agent E to write unit tests + run live E2E verification for the new dialog flow. The user had already indicated "I will test" earlier in the same conversation. I forgot, and ran QA on autopilot.

Root cause

Failed to re-read the user's recent constraints before dispatching the next agent. The QA-after-each-wave pattern was so ingrained that "I will test" was filtered out as noise instead of a hard constraint.

Impact

Wave 5.3 agent dispatch was rejected by the user. ~15 minutes wasted on the dispatch + context-loading of an agent whose output was never accepted. Trust slightly eroded — the user had to repeat themselves.

Rule going forward

Before dispatching any agent, scan the last 3 user messages for hard constraints. "I will test" is a hard constraint. "Don't refactor anything else" is a hard constraint. "Use null, not empty string" is a hard constraint. Hard constraints override the default workflow.

How to spot this in the future

If you're about to spawn an agent for QA/testing/verification, ask: "did the user say they want this, or am I autopilot-adding it?" If autopilot, drop the dispatch.

M2

Made up a fake SAR icon SVG

Severity: medium

What happened

For the Saudi Riyal currency icon on the Step 4 client-applications row-table price column, I hand-rolled a generic currency-S glyph. I never grepped the Falcon library first. The canonical <falcon-angular-saudi-riyal-icon> component already existed at libs/falcon/src/shared-ui/lib/components/falcon-saudi-riyal-icon/, and was wired into the svg-icon.registry.ts CURRENCY_SAR entry that the user eventually pointed me at.

Root cause

Assumed an icon that "feels generic" wouldn't be in the library. The Falcon library has 396+ exports. Anything currency-related, anything brand-related, anything domain-specific is almost certainly already there. The assumption was backwards.

Impact

A fake SVG shipped temporarily in the wizard. The user spotted it ("this doesn't look right"), pointed at the canonical icon, and Wave 6.1 + Wave 7 had to redo the API + the consumer template. Roughly 25 minutes of redundant work.

Rule going forward

Always grep the library for an existing component before writing inline SVG or inventing a glyph. Specifically:

  • libs/falcon/src/shared-ui/lib/components/ for icons
  • libs/falcon-ui-core/src/angular-wrapper/components/ for Falcon UI components
  • svg-icon.registry.ts for the named SVG registry

How to spot this in the future

If you find yourself typing <svg viewBox=...> inside a feature component, stop. Grep the library. The 396 exports are not all framework primitives — a lot of them are domain-specific icons and badges that have already been designed.

M3

Set defaults instead of null (repeated 2x)

Severity: medium

What happened

Initial emptyClient*() factories used '' for strings, 0 for numbers, and kept security: 'normal' and ownerRole: 'Account Owner' as defaults. The user wanted everything truly null so the UI could reflect "operator hasn't picked yet" and validation could enforce a conscious choice. It took 2 user messages and 2 agent dispatches before I widened the types from T to T | null and updated every factory.

Root cause

Interpreted "make it null" as "use the empty representation that won't trip the form." That is form-engineer's autopilot — Angular Reactive Forms historically punishes null. But the user was talking about state truth: nothing should be in the model until the operator chooses it. Two different mental models collided, and I didn't recognize it the first time.

Impact

Two full agent dispatches: the first kept defaults, the second only updated factories. A third pass widened the types in models/models.ts. Roughly 40 minutes of back-and-forth. User had to repeat themselves twice.

Rule going forward

"Make it null" means literally null. The sequence is:

  1. Widen the form interface types in models/models.ts first (string → string | null, etc.)
  2. Update every empty*() factory to return all-null
  3. Update validators to handle null (most "required" rules already do — confirm)
  4. Update the wire builder to coalesce null → wire-acceptable value (?? '', ?? 0, etc.) at the boundary

How to spot this in the future

When the user says "null" — literally search the code for empty-string and zero defaults in form state. If you see name: '', that's the trigger.

M4

Used raw SVG string API instead of content projection

Severity: medium

What happened

Designed the FalconAngularInputNumberComponent icon API as [iconLeftSvg]="rawSvgString" — consumer passes a raw SVG string. User pushed back: "passing just the class for the icon… easy peasy." The redesign in Wave 7 replaced the input with iconLeft boolean + <ng-content select="[falcon-input-number-icon-left]">. Consumer drops in the real icon component as a child.

Root cause

Stencil's underlying falcon-input-number-tw has an iconLeftSvg prop (because Stencil cross-framework consumers can't easily do projection). I mirrored that into the Angular wrapper without thinking. Angular has a richer story — content projection — and that's what an Angular consumer wants.

Impact

API was wrong-shaped in Wave 6.1 + half of Wave 7. Redesign required: new booleanAttribute input, new ng-content slot, new docs in the consumer (client-service-row-table). Roughly 30 minutes.

Rule going forward

When the consumer pattern is "drop in any icon/badge/action component," use <ng-content> projection — NOT raw string inputs. The whole reason a component library exists is so consumers don't pass strings of SVG. Keep the Stencil string prop for non-Angular consumers; the Angular wrapper layers ng-content on top.

How to spot this in the future

If you find yourself typing @Input() iconLeftSvg: string or [innerHTML] binding in a wrapper, stop. The Angular wrapper exists to be more ergonomic than the Stencil base. Slot-based composition is the more ergonomic choice every time.

M5

Row-table validation didn't render on Next click

Severity: high

What happened

Wave 6.1 added revealAllRowsErrors() to flip every row's touched signal so red borders would appear when the operator hit Next without filling required fields. It didn't work. The user saw zero visual feedback on Next click. The red state only appeared after manually focusing-and-blurring a dropdown inside the row. Wave 7 diagnosed the real cause and fixed it.

Root cause

OnPush child + signal-array input + reference-stable mutation. <falcon-angular-data-table> is OnPush. Its [data] input binds to rows(). When revealAllRowsErrors() updated each row's touched signal, the rows signal array reference DID NOT change (touched is a per-row signal living inside the row object). OnPush + signal change detection schedules a re-render only when the bound signal's tracked dependencies change for the child. Mutating a row-internal signal doesn't count.

Impact

User-reported bug. Surfaced after Wave 6.1 had already shipped + claimed live verification. Wave 7 had to re-investigate + diagnose + fix. ~45 minutes plus erosion of "live verified" trust. This is the most consequential bug of the session.

Rule going forward

OnPush + signal-array: reference identity matters. When you change a tangential per-item state (touched, focus, validity, expansion) that the OnPush child depends on, you MUST force a new reference on the upstream array. Pattern: 

this.rows.update((rs) => [...rs]);  // spread to force new ref

The defensive fix in Wave 7 also auto-set the touched key in setPriceType/setPriceValue so red state followed typing without needing blur — that's a separate quality-of-life win, but the core rule is the array spread.

How to spot this in the future

Whenever you write a method that mutates per-row state in a row-table or any OnPush list view, ask: "would the parent array's reference change as a result?" If no, add a spread. When in doubt, spread. The cost is one allocation per call; the benefit is correctness.

M6

Skipped checking existing enums

Severity: medium

What happened

Typed deliveryMethod in the form model as 'email' | 'sms' | 'both' | null — a string literal union. The user asked for an enum. The DeliveryMethod enum already existed at libs/falcon/src/shared-types/lib/enums/globels.ts:97 with Email=1, Sms=2, Both=3. The wire payload uses int values, not strings. My string-union shape would have shipped strings to the backend that the backend would have rejected.

Root cause

Same pathology as M2 — assumed the canonical type wasn't in the library and invented one. Didn't grep shared-types/lib/enums/ before designing the form model.

Impact

Caught during Wave 6.1 review before reaching the backend. Required a re-do of the form model + Step 3 template + wire builder. Roughly 20 minutes.

Rule going forward

Always grep libs/falcon/src/shared-types/lib/enums/ for an existing enum before inventing a new shape. If the user mentions an enum-y concept (status, type, method, role, level), assume it exists. Backend probably already uses the canonical version; using anything else means the wire builder has to translate.

How to spot this in the future

When you find yourself writing a string-literal-union for something the backend will consume, stop. Search the enums folder. Then check the Brain SK playbook for the page — the canonical enum is almost always listed in the wire-shape section.

M7

Stale Wave 4 popup vs Wave 4.2 toast confusion

Severity: low

What happened

In Wave 4, backend validation errors (HTTP 200 + isSuccessful:false) routed to the default rule in FALCON_HTTP_UI_CONFIG — a center popup. User wanted those as a top-right toast. I initially tried to bend the 4xx rule path to cover this, but those are different paths in the dispatcher: 4xx is for TRANSPORT errors; isSuccessful:false is application-layer.

Root cause

Conflated transport errors (HTTP 4xx/5xx, caught in the error handler arm of the observable) with application errors (HTTP 200 with a structured failure envelope, caught in the success arm via a "withMessages" hook). They look similar to the user — both are errors — but they go through different code paths in the dispatcher.

Impact

Wave 4.2 had to add a new 'applicationError' bucket to FalconHttpUiErrorBucket and a dedicated rule in the config. ~25 minutes.

Rule going forward

Backend validation errors (HTTP 200 + isSuccessful:false) → dedicated applicationError bucket, NOT 4xx, NOT default. The dispatcher's resolve-rule ladder has three rungs: HTTP status (4xx/5xx) → application bucket → default. Each rung is for a specific error class.

How to spot this in the future

When designing error UI for a new endpoint: ask whether the failure comes through the observable's error arm or its success-with-failure-envelope arm. If success-with-envelope, you need the application bucket. If error-arm, you're in the transport bucket.

M8

File size discipline broken twice

Severity: low

What happened

Original hierarchy-page-state.service.ts grew to 1080 lines before the Wave 5.1 refactor. Even after the split (1 facade + 6 slices + 3 helpers), the slice files landed at 285/196/175 LOC — within the soft 300-line cap, but models/models.ts hit 431 LOC and the user pushed back. A subsequent extraction into wire-builders.ts (254 LOC) brought models.ts down to 392.

Root cause

Treated 400 LOC as a hard ceiling I'd notice when crossed, rather than a soft cap I should eagerly extract around. Didn't include "is the file approaching cap?" as a pre-commit check.

Impact

User had to call out the breach. Refactor add-on. ~15 minutes.

Rule going forward

300–400 LOC is a SOFT cap. If a file is approaching 400, eagerly extract helpers/sub-modules before the wave ships. Pre-finish check: run wc -l on every file touched in the wave; anything >400 needs a justification or a pre-emptive extraction.

How to spot this in the future

When you find yourself adding "one more interface" to models.ts and the file is at 380 lines, that's the trigger. Extract the new shape to a sibling file like wire-builders.ts or .models.ts.

M9

Built unit tests that broke the workspace

Severity: low

What happened

Wrote 58 spec files for the Wave 4.2 routing + position config. They all failed with "No test suite found." After 30 minutes of debugging, root cause was incompatible versions: workspace had vitest@4 + @analogjs@2.1.3 + vite@6, but vitest 4 requires vite 7. Fix was downgrade vitest to 3.2.4 + upgrade @analogjs to 2.5.1. Then specs ran.

Root cause

Assumed the workspace's test runner worked. Workspace hadn't been run with vitest in weeks. Test infra rotted silently as other deps were bumped.

Impact

30 minutes of debugging before the first spec ran. Mood: frustrating.

Rule going forward

Before writing 30+ specs in a workspace that hasn't been run recently, sanity-test the runner first. One sanity.spec.ts with expect(1+1).toBe(2). Run it. Confirm green. THEN write the real specs.

How to spot this in the future

Look at the last commit date of vitest.config.ts or the lockfile. If it's been weeks, sanity-test before investing.

M10

Trusted live verification gates blindly

Severity: low

What happened

Across several waves I claimed "live verified via Chrome MCP." In some cases the renderer was frozen (the Wave 4 signal.set-in-switchMap bug) or the page was stale. The "live verification" was hollow — a green build hash + a screenshot that wasn't of the actual wave's UI.

Root cause

Took a screenshot, saw something rendered, declared success. Didn't reload first. Didn't verify the screenshot showed the new behavior, only that it showed the page.

Impact

False confidence shipped. Then real bugs surfaced in the next user message. Trust eroded — "live verified" started to feel meaningless.

Rule going forward

A green build hash ≠ a working runtime. Live verification requires:

  1. Kill the existing nx serve and start fresh (or hard-reload Chrome)
  2. Navigate to the scenario from a known-good starting state
  3. Re-run the exact user-reported flow
  4. Screenshot the post-state and reference the wave-specific element in the screenshot ("Step 5 now shows the generated password value")

How to spot this in the future

If your screenshot doesn't visually prove the new behavior, the verification is incomplete. "Page loaded" is not verification. "The button I just added is visible and clickable" is verification.

M12

@Input() iconLeft = false failed for bare attribute use

Severity: low

What happened

Wave 7 redesigned the input-number icon API. New template usage was <falcon-angular-input-number iconLeft> — bare attribute. Build failed with "string not assignable to boolean" because Angular treats bare attributes as empty strings, not true.

Root cause

Angular's strict template type-check enforces input types. A bare HTML attribute is parsed as "" (empty string). The input was typed boolean. Mismatch.

Impact

Build broke once after the Wave 7 commit. Fix was one-line: @Input({ transform: booleanAttribute }) iconLeft = false. ~5 minutes.

Rule going forward

When you want an @Input() to accept bare presence (HTML attribute style: <comp flag>), use @Input({ transform: booleanAttribute }). Import booleanAttribute from @angular/core.

How to spot this in the future

If you're adding a boolean input that consumers will use without an explicit value binding (just <comp flag> instead of [flag]="true"), use the transform. Same applies to numberAttribute for numeric inputs.

Anti-Pattern Catalog

10 patterns that surfaced this session that should never appear in Falcon code again. For each: the bad shape, the good shape, why the bad shape is wrong. Use these as Grep targets during code review.

1. Raw SVG string component inputs

Bad
// Component
@Input() iconLeftSvg?: string;

// Template
<falcon-input-number
  [iconLeftSvg]="'<svg>...</svg>'">
</falcon-input-number>
Good
// Component
@Input({ transform: booleanAttribute })
  iconLeft = false;
// + <ng-content select="[falcon-input-number-icon-left]">

// Template
<falcon-input-number iconLeft>
  <falcon-angular-saudi-riyal-icon
    falcon-input-number-icon-left>
  </falcon-angular-saudi-riyal-icon>
</falcon-input-number>

Why bad: raw SVG strings bypass the type system, lose accessibility attributes, break tree-shaking (SVG bytes inline), and force consumers to do unsafe [innerHTML] binding. Content projection lets the consumer drop in a real component with its own bindings, ARIA labels, and styling.

2. OnPush child with [data]=signal() where signal mutates but reference doesn't

Bad
revealAllRowsErrors() {
  for (const row of this.rows()) {
    row.touched.priceType.set(true);
    row.touched.priceValue.set(true);
  }
  // Array ref unchanged — OnPush child won't refresh
}
Good
revealAllRowsErrors() {
  for (const row of this.rows()) {
    row.touched.priceType.set(true);
    row.touched.priceValue.set(true);
  }
  // Force new array reference for OnPush
  this.rows.update((rs) => [...rs]);
}

Why bad: OnPush + signal arrays require reference change to trigger re-render in the child. Mutating per-item state inside the array doesn't change the array's reference, so the OnPush child sees the same input and skips change detection. Spread the array to force a new reference whenever you change tangential per-item state.

3. signal.set() inside RxJS switchMap reading a signal-derived observable

Bad
toObservable(this.selectedNode).pipe(
  switchMap((node) => this.api.fetch(node)),
  tap((data) => {
    this.dataSignal.set(data);
    // Angular flags: write-in-tracked-context
    // Renderer may freeze
  })
).subscribe();
Good
toObservable(this.selectedNode).pipe(
  switchMap((node) => this.api.fetch(node)),
  tap((data) => {
    untracked(() => this.dataSignal.set(data));
  })
).subscribe();

Why bad: when a RxJS pipe is fed by toObservable(signal) the downstream callbacks may run inside Angular's tracked context. Calling signal.set() there is "write-in-tracked-context" and can produce circular update warnings or — worse — silently freeze the renderer (the Wave 4 freeze bug). Wrapping .set() in untracked(() => …) tells Angular this write is not part of the reactivity graph and is safe.

4. @Input() flag = false for bare-attribute use

Bad
// Component
@Input() iconLeft = false;

// Template
<falcon-input-number iconLeft>...
// ERROR: '""' is not assignable to 'boolean'
Good
import { booleanAttribute } from '@angular/core';

@Input({ transform: booleanAttribute })
  iconLeft = false;

// Template
<falcon-input-number iconLeft>...
// OK — bare attribute coerced to true

Why bad: Angular's strict template type-checker treats bare attributes as empty strings. booleanAttribute is the canonical coercer: "" → true, "false" → false, anything else → true. Same family includes numberAttribute for numeric inputs.

5. Initializing form state with display defaults instead of null

Bad
emptyClientSettings(): ClientSettings {
  return {
    authority: 'Government',
    security: 'normal',
    userLimits: 100,
    // UI shows preset values — operator
    // never made a conscious choice
  };
}
Good
// Widen types in models/models.ts first
authority: AuthorityType | null;
security: SecurityLevel | null;
userLimits: number | null;

emptyClientSettings(): ClientSettings {
  return {
    authority: null,
    security: null,
    userLimits: null,
  };
}

Why bad: defaults masquerade as choices. The operator hits Next without ever seeing the field, but the form ships preset values that look like decisions. Required validation also can't enforce a conscious pick. Null = "operator hasn't chosen yet"; defaults silently bypass that signal. Coalesce at the wire-builder boundary, not in form state.

6. Putting state services in a central services/state/ folder when they belong to one component

Bad
// State lives outside its consumer
services/state/
  add-client-state.signals.ts
  add-client-step-1.signals.ts
  add-client-step-2.signals.ts
  add-client-step-3.signals.ts

// Wizard component reaches across folders
Good
// State lives next to its consumer
add-client-wizard/
  signals/
    add-client-wizard.signals.ts
    index.ts  // ADD_CLIENT_WIZARD_PROVIDERS
  client-information-step/
    signals/
      client-information-step.signals.ts
  client-settings-step/
    signals/
      client-settings-step.signals.ts

Why bad: central state folders create implicit cross-feature coupling and make it hard to delete a feature cleanly. State with a single component owner belongs inside that component folder. Provider hoisting at the wizard level guarantees pristine state on every re-open via Angular DI lifecycle. Page-wide state that genuinely spans multiple unrelated components (tree, users, drawer, settings) can stay at services/state/.

7. Building a feature without reading the Brain SK playbook for it

Bad
// Session start
// → open IDE
// → start typing form interfaces
// → invent the field list from React source
// → discover canonical enum 90 minutes later
// → discover backend wire shape 2 hours later
// → redo work
Good
// Session start
// 1. Read falcon-wiki/00-MOCs/AI-Agent-Onboarding.md
// 2. Read Brain SK CLAUDE.md
// 3. Read Brain Outputs/understanding/pages/
//      organization-hierarchy/Add Client/README.md
// 4. Read 06-STEP_5_ACCOUNT_OWNER.md
//        07-VALIDATIONS.md
//        08-BACKEND_API.md
//        12-ERROR_STATES.md
// 5. NOW start coding

Why bad: the playbook has the canonical wire shape, V-rule catalog, error code map, and enum decisions. Without it, you invent a shape that the backend will reject, miss validations the business wants, and design error UI for the wrong path. The playbook load is mandatory pre-read; treating it as optional is the single most expensive mistake you can make in a Falcon page session.

8. Routing HTTP 200 + isSuccessful:false through the default rule

Bad
// FALCON_HTTP_UI_CONFIG
rules: [
  { bucket: '4xx',     ui: 'toast', position: 'top-right' },
  { bucket: '5xx',     ui: 'dialog' },
  { bucket: 'default', ui: 'dialog' },  // catches isSuccessful:false
]
// Business validation errors show as center popup
Good
// FALCON_HTTP_UI_CONFIG
rules: [
  { bucket: '4xx',              ui: 'toast', position: 'top-right' },
  { bucket: '5xx',              ui: 'dialog' },
  { bucket: 'applicationError', ui: 'toast', position: 'top-right' },
  { bucket: 'default',          ui: 'dialog' },
]
// Backend validation goes to toast — same lane as 4xx

Why bad: HTTP 200 + isSuccessful:false is an application-layer error, not a transport error and not "everything else." Routing it through default conflates business validation with unexpected failures — the user sees a center dialog for what should be inline form feedback. Add the applicationError bucket and route it deliberately.

9. Letting per-step API fetches multiply

Bad
// Each step's constructor fetches its own data
clientInformationStep ngOnInit() {
  this.api.generatePassword();
  this.api.listAuthorityTypes();
}
clientSettingsStep ngOnInit() {
  this.api.listSecurityLevels();
}
// 5 steps = 5 separate fetch waterfalls
// Re-visiting a step re-fires its calls
Good
// Wizard mount fires one forkJoin
addClientWizard ngOnInit() {
  forkJoin({
    pwd:     this.api.generatePassword(),
    auth:    this.api.listAuthorityTypes(),
    sec:     this.api.listSecurityLevels(),
    channels:this.api.listCommChannels(),
    apps:    this.api.listApplications(),
  }).subscribe((data) => {
    untracked(() => this.state.cache.set(data));
  });
}
// Steps consume from cached signals — zero new XHR

Why bad: per-step fetches mean the wizard is at the mercy of the slowest step's API on every navigation. They re-fire on back/forward. They make caching state per-step instead of per-wizard. One forkJoin on mount gives the operator the full wizard's data on entry; navigation between steps is local-only.

10. Trusting a green build hash to mean working runtime

Bad
// Wave wrap-up
1. nx build admin-console
2. Hash: fcbef6de9dbc5d9f — GREEN
3. Open Chrome MCP, take screenshot
4. Screenshot shows the page rendering
5. Report: "live verified"
Good
// Wave wrap-up
1. nx build admin-console — GREEN
2. Kill existing nx serve
3. nx serve admin-console
4. Hard-reload Chrome (Ctrl+Shift+R)
5. Run the exact user-reported scenario
6. Screenshot showing the NEW behavior (the
   specific element/state the wave introduced)
7. Report: "Step 5 generated-password value
   = 'xK9!mP2qR' rendered at "

Why bad: a green build hash means TypeScript compiled and bundling succeeded. It does not mean the renderer didn't freeze, the signal didn't write into a tracked context, the OnPush child didn't skip re-render, or that the new wave's UI is actually showing on screen. Live verification is hard-reload + scenario re-run + screenshot of the wave-specific element.

Standing Rules Codified

The 10 operational rules and 6 architectural doctrines from the session memory file. These are the durable artifacts — what every future Ammar session that touches a Falcon wizard should apply.

Operational rules (10)

  1. "Make it null" means literally null — widen types first
    Any time the user asks for null defaults, or whenever you design form state from scratch. Widen T → T | null in models/models.ts BEFORE updating factories.
  2. OnPush + signal-array: reference identity matters
    When you change a tangential per-item state (touched, focus, validity) that an OnPush child depends on. Force a new array reference with signal.update(arr => [...arr]).
  3. No raw SVG strings in component APIs — use ng-content projection
    Designing any Falcon wrapper component that accepts an icon, badge, or action slot. Use <ng-content select="[slot-name]">, not @Input() iconSvg: string.
  4. Always grep libs/ for existing enums/icons/components before inventing
    Whenever you're about to type an inline SVG, a string-literal union, or a new component. Grep: libs/falcon/src/shared-types/lib/enums/, libs/falcon/src/shared-ui/lib/components/, libs/falcon-ui-core/src/angular-wrapper/components/.
  5. Test runner must be sanity-tested before writing 30+ specs
    In any workspace where vitest hasn't been run in > 1 week. Write a single sanity.spec.ts with expect(1+1).toBe(2). Run it. Confirm green. Then commit to the real spec suite.
  6. untracked() for signal.set inside RxJS pipes that read signals via toObservable
    Any RxJS pipeline fed by toObservable(signal) where a downstream callback calls .set() on another signal. Wrap the .set() in untracked(() => …) to escape tracked context.
  7. Load Brain SK CLAUDE.md + the page-specific playbook before starting
    Session start for any Falcon page-level user action. The 8 verification questions in IMPLEMENTATION_KNOWLEDGE_MAP.md are the gate — you haven't loaded enough until you can answer all 8 with file citations.
  8. @Input({ transform: booleanAttribute }) for bare-attribute boolean inputs
    Any boolean input you expect consumers to use as a bare HTML attribute (<comp flag> rather than [flag]="true"). Import booleanAttribute from @angular/core.
  9. Backend validation errors (HTTP 200 + isSuccessful:false) → applicationError rule
    Designing error UI for any new endpoint. If failures come through the observable's success arm with a failure envelope, you need the 'applicationError' bucket — NOT 4xx, NOT default.
  10. "I will test" → don't autopilot live verification
    Before dispatching an agent for QA or running a Chrome MCP session. Scan the last 3 user messages for hard constraints. "I will test" is one of them.

Architectural doctrines (6)

A State lives next to its consumer (per-component signals folder)

Per-component state goes inside the component folder at signals/. No central services/state/ for state with a single component owner. Page-wide state spanning multiple unrelated components is the exception.

B Provider hoisting at the wizard component level (pristine state via DI lifecycle)

Per-step signal services are @Injectable() (no providedIn). They get provided once at the wizard component via providers: [...ADD_CLIENT_WIZARD_PROVIDERS]. Each wizard mount creates fresh instances; no manual reset cascade.

C Eager loading on wizard mount (one forkJoin, steps consume from cache)

Every API dependency the wizard needs across its steps fires in one forkJoin on mount. Steps read from cached signals. Step navigation fires zero new XHRs. Cache resets on wizard close.

D Content projection > raw-string inputs (for icons, badges, actions)

Component slots use <ng-content select="[slot-name]">. Consumer drops in a real component with its own bindings. Never [innerHTML], never SVG strings.

E OnPush + signal arrays — force new reference on tangential state change

When you change a per-item state (touched, focus) that an OnPush child depends on, the parent array reference must change too. Spread is the canonical fix: signal.update(arr => [...arr]).

F Pure helpers for testability — extract routing/extraction logic from services

Logic that doesn't need Angular DI lives in standalone .ts files (e.g. falcon-http-ui-routing.ts). Services delegate. Tests hit the helper directly without TestBed bootstrap. Faster, more focused, no Angular zone or DI noise.
