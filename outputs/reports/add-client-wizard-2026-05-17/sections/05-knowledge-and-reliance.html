Deep dive — what each source gave me

The percentages above are not just symbolic — each one represents concrete decisions that would have gone the wrong direction without that source. Below is a deep dive into every source, with a representative example of the kind of decision it unlocked.

Falcon Brain Outputs — Add Client page playbook

Located at C:\Falcon\Brain Outputs\understanding\pages\organization-hierarchy\Add Client\. This is the canonical 17-file implementation spec covering frontend wireframes, backend API, validations, error states, and Kafka side-effects.

Falcon library

Existing Falcon library codebase

The libs/falcon-ui-core/ and libs/falcon/ trees — the wrapper-component pattern, Stencil components, content-projection conventions, the SVG icon registry, and the existing dialog components.

Following an existing pattern is faster than inventing and produces parity with the rest of the library.

Add User wizard

Add User wizard reference implementation

The Add User wizard was shipped previously and was the closest pattern match for Add Client. It established the per-step validation folder pattern, the field-level error map, and the async-pending decoration pipeline.

Concrete example: The FIELD_LEVEL_ERROR_MAP in Add User — mapping backend error codes to specific form fields + a step-jump action — was the canonical pattern I copied for Add Client. Same for generatePassword('normal') upfront on wizard mount instead of on Step 5 entry.
12%
Angular signals

Angular 17+ signals + RxJS interop knowledge

Knowledge of signal() / computed() / effect() / untracked() / toSignal() / toObservable(), plus the OnPush reference-identity trap for signal arrays.

Concrete example: The wizard renderer froze when signal.set() was called inside a switchMap. The fix required knowing that signal writes inside reactive contexts (like RxJS pipes started by toObservable) need to be wrapped in untracked(() => ...) to escape implicit tracking. This is not common knowledge — most Angular tutorials don't cover this.

React source of truth — Falcon-Taha2 admin/addclient.jsx

Falcon brain skills — frontend rules

noor-instructions (layout ownership, theme promotion, color palette over intent), angular-tailwind-skill (Tailwind utilities only — no SCSS, no PrimeNG, no component CSS), nx-workspace-skill (project structure norms).

TS / DI

TypeScript / Angular DI knowledge

Page-scoped providers: [...] vs providedIn: 'root', inject() patterns, viewChild() refs, content-projection slot selectors, the booleanAttribute transform for bare-attribute inputs.

Concrete example: The per-step signal services were marked @Injectable() (no providedIn) and hoisted via the wizard's providers: [...ADD_CLIENT_WIZARD_PROVIDERS]. This guarantees pristine state on every wizard re-open via Angular DI lifecycle — no manual reset cascade needed. Choosing root-providers instead would have caused state leakage between sessions.

Prior memory

Wave 4 + 4.1 + 4.2 prior session memories

The memory files from immediately preceding sessions on the same feature. Locked the toast position (top-right), the applicationError rule introduction, and the dispatcher's resolve-rule ladder.

Concrete example: Toast position was top-left in Wave 4.1, then changed to top-right per user feedback in Wave 4.2. The memory file recorded this. Without it, I might have rebuilt the position-mapping spec from scratch in Wave 5 and re-defaulted to top-left.
4%
HTTP / API

HTTP / REST API design knowledge

forkJoin for parallel requests with shared result tuple, catchError per-inner-call so one failure doesn't kill all, mime-type to extension mapping, base64 image encoding.

Concrete example: Eager loading on wizard mount fires 5 APIs in a single forkJoin. Each inner observable has its own catchError so if comm-channels lookup fails, applications and password-gen still load. Steps render with degraded but functional state. Without per-call catching, one slow service kills the whole wizard.
3%
Test infra

Vitest / Vite / Angular testing

@analogjs/vitest-angular setup, provideZonelessChangeDetection(), TestBed.configureTestingModule(), why @Input() bare-attribute needs booleanAttribute.

Concrete example: Vitest 4 needs Vite 7. The workspace had Vite 6 + @analogjs 2.1.3. After 30 minutes of "No test suite found" errors, downgrading vitest to 3.2.4 + upgrading @analogjs to 2.5.1 brought the runner back. Without knowing the version compatibility matrix, I would have flailed for another hour.

All three are documented or codified in the repo — not in my general training data. This means session quality is dominated by whether I successfully load these sources upfront, not by raw model capability.
