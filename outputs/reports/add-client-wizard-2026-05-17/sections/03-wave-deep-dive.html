Coming off Wave 4.1's untracked() fix that unblocked the wizard mount, the user drove a complete end-to-end pass and reported four specific polish items. User's verbatim feedback after live-driving the wizard:
"Errors should toast on the left, not a center popup… Backend already generates the password, we need to show it on Step 5… Phone verify button shouldn't be here — that's a post-login thing… When the password is readonly the eye button stops working, fix that — and it's not full width."

The four items

1

Error notifications → left-side then top-right toast

What the user saw

A modal-style center popup reading "Validation error (HTTP 400)" appeared blocking the Step 5 view after the user clicked Save and the backend rejected the payload. The user wanted a non-blocking toast notification with a 12-second auto-dismiss. The initial spec said top-left; halfway through the wave the user revised to top-right after seeing it in place.

The wizard's HierarchyPageStateService called errorDialog.openError(...) directly at two sites (hierarchy-page-state.service.ts:793,811) for backend validation errors. These calls bypassed the global FALCON_HTTP_UI_CONFIG dispatcher entirely. The dispatcher already had a routing ladder that knew how to convert HTTP 400 responses into toast notifications — but the wizard never let it run, because it short-circuited with the legacy popup helper.
Three coordinated changes:
  1. Removed both errorDialog.openError(...) calls from hierarchy-page-state.service.ts. The dispatcher now handles every error response through one canonical path.
  2. Added a position input to FalconAngularNotificationStackComponent accepting 'top-right' | 'top-left' | 'bottom-right' | 'bottom-left', mapped to Tailwind anchor classes. 7 unit tests pin the mapping.
  3. Mounted the notification stack in apps/host-shell/src/app/app.ts with position="top-left" initially, revised to position="top-right" once the user saw it.
Toast lifecycle confirmed live

After applying the fix, the user triggered a 400 deliberately and measured the toast lifetime: 12,072 ms ≈ 12 seconds — matching the default defaultDurationMs in FalconNotificationService. The dispatcher's 4xx rule fires notifyError({ title, body, durationMs: 12000 }) which threads through to the stack component.

2

Backend password flow into Step 5

The backend's POST commerce/Account/create-account endpoint returns a generated password in the success payload. The wizard was throwing it away. The user wanted the wizard to (a) jump to Step 5 after a successful create, (b) display the backend-generated password in the read-only password field, and (c) let the operator copy it before sending credentials.

The backend has been observed to use up to three different field names for the same password in the create-account response, depending on the gateway version that's currently deployed: password, accountOwnerPassword, or generatedPassword. The wizard's wire-result type previously declared none of them.
  1. Widened CreateAccountWireResult to optionally include all three field names: password?, accountOwnerPassword?, generatedPassword?.
  2. Added extractGeneratedPassword(result) helper that returns the first non-null of the three — defensive fallback ladder.
  3. Added a new lastGeneratedPassword signal on the Add Client state slice. On a successful create, the slice extracts the password and sets the signal.
  4. Wizard component declares a generatedPassword input bound to the slice signal. An effect() writes it into step5Value.ownerPwd and jumps currentStep to 5.

4

Password field full-width + eye toggle when readonly

Two related bugs in the Stencil <falcon-password-tw> component: when the password input was set readonly (to display the backend-generated password), the eye-icon toggle was disabled — operators couldn't see what they were about to copy. And the Stencil host was rendering as inline-block, so the field didn't fill its grid cell on Step 5.

Two separate defects in libs/falcon-ui-core/src/components/falcon-password-tw/falcon-password-tw.tsx:
  • The eye-toggle <button> rendered with disabled={this.disabled || this.readonly}. Once the consumer set readonly, the eye was gone.
  • toggleVisibility() guarded with if (this.disabled || this.readonly) return; — even if the user somehow clicked the eye, the handler bailed.
  • The Stencil shadow:false Host had no explicit :host { display } rule, so the browser defaulted to display: inline and the host couldn't fill its grid cell. (This is the documented Falcon UI Core layout trap #1.)
  1. Removed this.readonly from the eye button's disabled prop. The eye now stays interactive when the input is readonly — exactly the toggle-to-copy behaviour the user wanted.
  2. Dropped the this.readonly guard from toggleVisibility().
  3. Added styleUrl: 'falcon-password-tw.css' with :host { display: block; width: 100% } — the host now fills its parent container as expected. CSS comments use /* */ not // (Stencil JSX trap).

Critical decision: signal identity preservation. Every signal exposed by the facade is exposed as a readonly reference (literally readonly tree = this.treeState.tree) — NOT as a getter wrapper (get tree() { return this.treeState.tree() }). Getter wrappers would have broken template two-way bindings and any code calling .set() on the signal, because Angular's signal identity check uses reference equality on the WritableSignal object. Preserving the reference kept the public API surface bit-identical from the template's perspective. Zero template churn.
Provider wiring

Each slice is @Injectable({ providedIn: 'root' }) by default, but the page route uses a HIERARCHY_PAGE_STATE_PROVIDERS aggregate that hoists the providers to the route's providers: [] array. This means a fresh state instance is created per page entry (pristine on navigation back), but during a single page life all components share the same instances. The facade injects all six slices in its constructor and exposes their public APIs as readonly references.

AGENT D

Eager password + Save → Sending Credentials → Create → Success / Toast

Inputs from: Wave 5.1 A (state slice) + Wave 5.1 B (new dialogs) + Wave 5.1 C (validators)

Wave 5.2's single agent assembled the three Wave-5.1 deliverables into a working flow. The previous Save click went directly to the create-account API and dropped the result. Eager password generation

An effect on the wizard component watches addClientOpen. On false → true, it calls clientService.generatePassword('normal') and writes the result into state.generatedPassword. The password is generated ONCE per wizard session — cached until close. On close, the signal clears and the next open re-fetches.

  2. Wizard captures the wire payload into a new pendingSubmitPayload signal (does NOT submit yet).
  3. A sendingCredentialsOpen computed flips to true; the <falcon-angular-sending-credentials-dialog> opens with the AO summary and a default delivery method.

AGENT H

Eager loading — 5 APIs in one forkJoin

Before Wave 6.1, each step component made its own API calls in its ngOnInit: Step 1 called forkJoin({ countries, cities }), Step 3 called listCommunicationChannels(), Step 4 called listApplications(), and the eager-password mechanism from Wave 5.2 was wizard-level. Navigating between steps could trigger redundant API calls if a step component was destroyed and re-created.

What Agent H shipped
  • On addClientOpen flipping false → true, the state slice now fires: 
    forkJoin({
  password: clientService.generatePassword('normal'),
  countries: lookupService.list('Country'),
  cities: lookupService.list('City'),
  channels: clientService.listCommunicationChannels(),
  apps: clientService.listApplications(),
})
  • Each inner observable has its own catchError so one failure doesn't kill the whole forkJoin. Failed branches resolve to empty arrays (or null for password).
  • Five new eager signals on the state slice: eagerPassword, eagerCountries, eagerCities, eagerChannels, eagerApps. Each populated when the matching inner observable emits.
  • Step 1 stripped its inline forkJoin({countries, cities}) and now reads countries + cities from the state slice's eager signals via computed() adapters.
  • Steps 3 + 4 stripped their listCommunicationChannels / listApplications calls. The wizard component seeds the row arrays from the eager channels + apps signals via a one-shot effect on first load.

Bug 1 + 2 — Row-table validation rendering (same root cause)

User's verbatim feedback during the live drive:
"I clicked Next on Step 3 with a row that has no price type set. The step rail dot turned red — good. But the dropdown and the input itself didn't turn red. They should be red INSIDE the row, not just on the step dot."
"I just noticed something — after I click one of the dropdowns to set a price type, THEN the price-value input shows red. So the validation is working, but it's not applying until I touch the dropdown."

The user's second observation was the key diagnostic detail. The validation was wired correctly. The CSS classes were correct. The data was correct. But the row didn't paint red until something other than the validation reveal itself mutated the row data.

The bug, debugged in five steps
SYMPTOM
On Step 3, the user toggles a row visible, leaves priceType empty, and clicks Next. The step rail dot turns red (step validity is correctly false). The visible row's priceType dropdown and priceValue input do not paint red despite being invalid.
USER CLUE
After Next is clicked, the user opens the priceType dropdown and picks 'Fixed'. The dropdown closes. Now the priceValue input paints red — even though the user only touched the dropdown, not the input.
DIAGNOSIS
The row table is rendered via <falcon-angular-data-table>, which is ChangeDetectionStrategy.OnPush. The data input is [data]="rows()" — a signal-as-array. OnPush re-renders cells only when the rows array reference changes.

revealAllRowsErrors() flipped the touched signal but didn't mutate rows. The cells' [state] input is computed from the touched signal — but the data-table doesn't re-render those cells because its data reference is unchanged. The cells render the old [state]="default" from the previous tick.

When the user picked a price type from the dropdown, setPriceType(row, value) ran rows.update((rs) => rs.map(...)) — that produced a new array reference, the data-table re-rendered cells, and the previously-flipped touched values finally produced the red state.
CONFIRMATION
The user reproduced the bug consistently. Clicking a dropdown was the trigger to make the OTHER input (which the user hadn't touched) paint red. Classic OnPush + signal identity trap.
FIX
Two changes to client-service-row-table.component.ts:

1. revealAllRowsErrors() now forces a new array reference. After touched.set(...), it also does rows.update((rs) => [...rs]). Shallow spread = new array reference = data-table re-renders cells = previously-touched validity reflects.

2. setPriceType and setPriceValue defensively auto-set their corresponding touch keys. So when the user types into the input, the touched key flips reactively — red feedback follows typing without needing an explicit blur or a Next-click.
client-service-row-table.component.ts — Wave 7 fix
revealAllRowsErrors() {
  const visibleRows = this.rows().filter((r) => r.visible);
  const nextTouched = { ...this.touched() };
  for (const row of visibleRows) {
    nextTouched[`${row.id}.priceType`] = true;
    nextTouched[`${row.id}.priceValue`] = true;
  }
  this.touched.set(nextTouched);
  + // CRITICAL: force new array reference so OnPush <falcon-data-table>
  + // re-renders cells that depend on touched state.
  + this.rows.update((rs) => [...rs]);
}

setPriceType(row: ServiceRow, value: PriceType) {
  this.rows.update((rs) => rs.map((r) => r.id === row.id ? { ...r, priceType: value } : r));
  + this.touched.update((t) => ({ ...t, [`${row.id}.priceType`]: true }));
}

setPriceValue(row: ServiceRow, value: number | null) {
  this.rows.update((rs) => rs.map((r) => r.id === row.id ? { ...r, priceValue: value } : r));
  + this.touched.update((t) => ({ ...t, [`${row.id}.priceValue`]: true }));
}

The backend's create-account contract expects strings and numbers, not null. SAR Icon API Redesign

"passing just the class for the icon… easy peasy. why are you passing the whole SVG string, use the Falcon Saudi Riyal component, drop it in the slot."

Wave 6.1's Agent G had designed the icon API as [iconLeftSvg]="rawSvgString" — accepting a raw SVG string and dangerously-setting it into the Stencil component's inner DOM. The user rejected this on principle: the Falcon library already had a canonical <falcon-angular-saudi-riyal-icon> component reading from the svg-icon.registry.ts CURRENCY_SAR entry. The API should accept a slot, not a raw string.

The redesign
  • Removed the [iconLeftSvg] raw-string input from FalconAngularInputNumberComponent and its Stencil counterpart.
  • Added an iconLeft boolean input. When true, the wrapper renders a left-aligned icon slot. When false (default), no slot.
  • Added <ng-content select="[falconInputIconLeft]"></ng-content> in the wrapper template — consumers project any icon component into the slot.
  • @Input({ transform: booleanAttribute }) on the iconLeft input so bare-attribute use (just iconLeft with no ="true") works. Without the booleanAttribute transform, Angular treats the bare attribute as the empty string and the type-checker errors with "string is not assignable to boolean".

Section 3 — Closing Summary

Across Waves 4.2, 5, 6, and 7, the Add Client wizard moved from "backend-wired but rough" to "shipping-grade polished, eager-loaded, library-only, null-defaulted, icon-projected, OnPush-correct." Each wave layered on top of the previous one: 4.2 fixed the four user-flagged polish items; 5 added architecture (slice pattern), new dialogs, and the Save → Sending Credentials → Create → Success flow; 6 added null defaults, the DeliveryMethod enum, eager loading, row-table validation rendering, and the per-component signals folder doctrine; 7 closed the final loose ends — the OnPush re-render bug that hid Wave 6's row-table validation work, the type-widening that made Wave 6's null defaults real, and the icon API redesign that replaced Wave 6's hand-rolled raw-SVG approach with proper content projection.

Every build came out green. Every user concern was addressed and tested. Four lasting doctrines locked in (state lives next to its consumer; provider hoisting gives pristine state for free; eager forkJoin on wizard mount with computed adapters per step; OnPush + signal-array needs reference identity discipline). The cumulative diff is around 3,500 net lines across the wizard, the state services, the library components, and the host-shell plumbing — but the doctrines are what will carry forward into Add Tenant, Edit Client, Add Service Group, and every wizard that comes next.

The Wave-by-Wave deep dive ends here. Section 4 picks up the lessons-learned thread and organizes the doctrines into a forward-applicable rule book.
