2. Original Problem Statement

The user wanted a working 5-step Add Client wizard with the following non-negotiable requirements, captured verbatim across Wave 4.2, Wave 5, Wave 6, and Wave 7 user messages:

Pillar What the user asked for
Backend integration All 6 Add Client APIs (lookups, async account-name check, generate-password, create-account) must fire live against the local Identity Gateway and System Gateway. ServiceOperationResult<T> envelope honored. Token-bearer auth required.
Proper validation Each step gets its own validations/validations.ts folder mirroring Add User wizard. Per-field inline messages, red borders on touch, Next disabled when invalid, stepper-rail dot paints red on Next click for invalid steps.
Business-validation toasts HTTP 200 + isSuccessful:false (business validation errors) must render as a top-right red toast showing the backend's exact errorMessages[0] string — not a centered confirmation popup, not a generic "Bad request" body.
Eager loading All 5 wizard APIs (generate-password, country lookup, city lookup, communication channels, applications) must fire in one parallel forkJoin on wizard mount. Navigation between steps must produce zero new XHR. Close + reopen fires a fresh batch.
Null-init defaults Every form field begins literally null. No '' for strings, no 0 for numbers, no 'normal' security default, no 'Account Owner' role default. Types widened to T | null; wire builder coalesces at the boundary.
Per-component signal architecture Each step's signals live INSIDE that step's component folder (<step>/signals/<step>.signals.ts). Wizard-wide signals live in add-client-wizard/signals/. No central services/state/ for state with a single component owner.
Pixel parity to React mockups The new Sending Credentials + Completion Success popups must match the React source-of-truth (C:\Falcon\Source_of_truth_theme\React\Falcon-Taha2\admin\addclient.jsx lines 680–767) — same 3-method-card layout, same illustrations, same auto-dismiss timer, same click-anywhere-to-dismiss behavior.
Falcon library only Zero native <button> / <input> / <dialog>. Every interactive element is a Falcon wrapper (<falcon-angular-*>). Missing component = extend the library, do not hand-roll.
Constraint of constraints: the user said "I will test" — so live verification was the user's responsibility, and the agent's job was to ship build-green + visually-correct code on every wave without autopiloting Chrome MCP E2E runs.

3. End-to-End Process Flow

This is the final shape of the user journey from the click that opens the wizard to the routing call that closes it. Every step below is annotated with the signals, APIs, and components that participate. Read top-to-bottom — the flow is strictly linear with two terminal branches at step 9 (success vs. error).

STEP 1 User clicks "Add Client" from Org Hierarchy
From the management-console org-hierarchy-page, the user opens the root-action menu and selects Add Client. HierarchyPageStateService (facade) routes to addClientState.openWizard(), which flips the addClientOpen signal false → true. The wizard mounts via Angular DI — providers are hoisted at AddClientWizardComponent via ADD_CLIENT_WIZARD_PROVIDERS, guaranteeing pristine state on every re-open.
STEP 2 Wizard mount fires forkJoin of 5 APIs in parallel
ngOnInit on AddClientWizardComponent calls clientService.prefetchWizardData() which forks 5 calls. catchError is applied per-inner so a single failure does not kill the batch.
  • POST /user/generate-password (Identity Gateway, port 8088) — returns one-shot strong password
  • GET /commerce/Lookup/{countryId} (System Gateway, port 7256) — country option list
  • GET /commerce/Lookup/{cityId} (System Gateway) — city option list
  • GET /commerce/CommunicationChannel (System Gateway) — available channels for Step 3 rows
  • GET /commerce/Application (System Gateway) — available applications for Step 4 rows
STEP 3 Results land in wizard-level signals (single source of truth for cached data)
The 5 responses unzip into 5 wizard signals stored in add-client-wizard.signals.ts:
  • eagerCountries — country lookup array
  • eagerCities — city lookup array
  • eagerCommChannels — communication channel rows for Step 3
  • eagerApps — application rows for Step 4
  • lastGeneratedPassword — pre-filled password for Step 5
Steps READ from these signals — they do not own them. On closeWizard() the signals are cleared so the next open fires a fresh batch.
STEP 4 Step 1 — Client Information
Country/city dropdowns bind to eagerCountries / eagerCities — no fresh XHR. All form fields start literally null (Wave 7 widened types to T | null across models.ts). The accountName field runs async uniqueness check via POST /commerce/Account/account-name-availability on debounceTime(300) from the value-change pipe — untracked(() => ...) wraps every signal.set inside the switchMap to prevent renderer freezes that Wave 4 originally hit.

Photo upload emits the canonical object shape: { extension: 'png', fileBase64String: '...' }, written into step1Value().info.profilePictureImageInfo. The <app-falcon-photo-uploader> component gained a pictureChange output in Wave 6 to surface this shape (backward-compatible with the existing photo data-URL model used for preview).
STEP 5 Steps 2, 3, 4, 5 — pure view + form (no new XHR)
Navigation between steps does NOT trigger network calls. Each step:
  • Step 2 — Client Settings: security mode + IP allowlist + 3 user/session limits — all null-init (Wave 7). Step starts isFormValid === false until user picks a security mode.
  • Step 3 — Communication Channels: reads eagerCommChannels into the shared <client-service-row-table> editor. Per-row priceType + priceValue with the new Saudi Riyal left-icon on the <falcon-angular-input-number>.
  • Step 4 — Applications: identical row-table component, fed from eagerApps. Same validation cascade.
  • Step 5 — Account Owner: form fields all null-init (no 'Account Owner' role default). Password field pre-filled from lastGeneratedPassword; eye toggle works even when input is readonly (Wave 4.2 library fix in falcon-password-tw.tsx).
STEP 6 Row-table validation cascade (Step 3 + 4)
When the user clicks Next on Step 3 or 4 with an invalid row, revealAllRowsErrors() runs. Wave 7 hardened this to fix an OnPush re-render bug — in addition to flipping touched signals, it now also calls this.rows.update((rs) => [...rs]) to force a new array reference on the data-table input. Without this spread, the OnPush <falcon-angular-data-table> child would retain stale cell renderers and the red borders would only appear after a manual dropdown click.

Touch keys (priceTypeTouched, priceValueTouched) are also defensively auto-set inside setPriceType() / setPriceValue() so the red state follows typing without needing a blur event. The stepper-rail dot's color binds to step.isFormValid(), so an invalid step paints red on Next click.
STEP 7 Save click on Step 5 → opens Sending Credentials popup
Clicking Save on Step 5 does NOT submit yet. Instead, the wizard signals service flips sendingCredentialsOpen.set(true), which mounts the new <falcon-angular-sending-credentials-dialog> component (library addition from Wave 5.1). The popup is fed:
  • ownerName, ownerEmail, ownerPhone from step5Value()
  • defaultDelivery — Email by default
The popup renders the 3 method cards (Email / SMS / Both) + the AO summary block + Cancel/Send buttons. Pixel parity to React source at addclient.jsx:680-749.
STEP 8 User picks Email/SMS/Both → maps to DeliveryMethod enum → POSTs create-account
The popup emits (send)="onSend('email'|'sms'|'both')". The wizard signals service maps the string to the canonical DeliveryMethod enum (libs/falcon/src/shared-types/lib/enums/globels.ts:97) — Email = 1, Sms = 2, Both = 3. Wave 6 corrected this; before Wave 6 the wire field was a string. buildCreateAccountWireRequest() in wire-builders.ts assembles the full payload — all 5 step states, photo objects, delivery method int, owner info — and the service issues:

POST /commerce/Node/create-account (System Gateway, bearer token forwarded).

While the call is in-flight, pendingCreate.set(true) drives a busy state on the popup's Send button.
STEP 9-A Success branch (HTTP 200 + isSuccessful:true)
The dispatcher's FALCON_HTTP_UI_CONFIG resolves the response as success — no rule fires. The wizard signals service:
  • Closes the Sending Credentials popup (sendingCredentialsOpen.set(false))
  • Opens the Completion Success popup (completionSuccessOpen.set(true))
  • Starts the 10s auto-dismiss timer (configurable via autoDismissMs)
The <falcon-angular-completion-success-dialog> renders the clipboard-with-checkmark illustration + title + subtitle. Click anywhere OR timer elapses → emits (closed). The wizard listens and calls router.navigate(['/admin-console/org-hierarchy-page'], { queryParams: { selectedNode: id } }) — returning to the org-hierarchy with the new client pre-selected.
STEP 9-B Business validation error branch (HTTP 200 + isSuccessful:false, OR 422)
Backend returns the success envelope with isSuccessful: false and an errorMessages array. The dispatcher's resolver routes this to the applicationError rule (Wave 4.2 addition to FalconHttpUiErrorBucket union). The rule:
  • Title from the rule's title field (i18n key or category default)
  • Subtitle = backend's errorMessages[0] via extractInBodyErrorDetail
  • Render mode: top-right toast (red, error intent), 5s auto-dismiss
Field-level errors map back to the originating step via FIELD_LEVEL_ERROR_MAP (e.g. VAL_010 → Step 1 accountName, VAL_023 → Step 5 ownerEmail). The toast appears in the host-shell's mounted <falcon-angular-notification-stack position="top-right">.
STEP 9-C Transport error branch (5xx, network failure)
Genuine transport failures (500, 502, network drop) still route through the existing FalconHttpErrorDialogService — a centered confirmation popup with retry. This path was unchanged in this session; the Wave 4.2 fix kept it intact while carving out the applicationError bucket for business validation specifically. The user can dismiss the popup and the wizard remains open with its filled-in state preserved.
Performance characteristic: the entire wizard session, from open to close, costs 5 parallel XHR on mount + 1 sequential POST on save. Zero per-step API chatter. Verified via DevTools Network panel: navigating Step 1 → 5 in any order produces zero new requests.
