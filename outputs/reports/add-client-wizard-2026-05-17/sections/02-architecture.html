2.2 — State Architecture

The Add Client wizard runs on a three-layer DI cake: page → wizard → step. Each layer owns the state that survives at its own lifecycle. Provider hoisting at the wizard component guarantees that wizard-scoped step services are destroyed on close and recreated on reopen — no manual reset cascade is needed for pristine state.

2.2.a — The four-step layered model

  1. Page route (org-hierarchy-page.routes.ts) declares the HIERARCHY_PAGE_STATE_PROVIDERS aggregate. This aggregate registers the 5 surviving page-level slices AND the wizard-wide AddClientWizardSignalsService. Lifetime: as long as the page route is active.
  2. Facade HierarchyPageStateService (slim 338-LOC re-exporter) injects the 5 page slices and the wizard-wide signals service. It re-exports their public surface so existing consumers (page menu, settings tab, user-details page) compile against a single facade rather than 6 separate services.
  3. Wizard component (add-client-wizard.component.ts) declares providers: [...ADD_CLIENT_WIZARD_PROVIDERS] in its @Component decorator. This hoists the 5 per-step signal services into a wizard-scoped sub-injector. When the parent template's @if state.addClientOpen() falls, Angular destroys this sub-injector → all 5 step services drop with it.
  4. Per-step signal services live inside their step folders: <step>/signals/<step>.signals.ts. Each is a plain @Injectable() (no providedIn) exposing 4 signals — value, valid, dirty, revealed — plus a reset() method. The wizard binds [(value)]="state1.value" on each step via viewChild() refs.

2.2.c — Why this split?

Layer Scope Why this level?
Page slices (tree, users, drawer, settings, add-user) Page route Each spans multiple components on the page. No single owner. Lives as long as the operator is on Organization Hierarchy.
AddClientWizardSignalsService Page route The page menu sets addClientOpen.set(true) before the wizard component exists. The wizard then injects the SAME instance via DI walk-up. Also keeps the eager-loaded catalogs warm if the wizard closes + reopens within the same page session.
5 per-step signal services Wizard component (via providers) Wizard mount/unmount drives their lifecycle. Pristine state on every reopen without an explicit reset call — Angular's DI lifecycle does it for free. The optional reset() method exists for a future "Start Over" button mid-wizard.

2.5 — Per-Component Signals Doctrine (forward-applicable)

Wave 6.2 (Agent I) formalized the doctrine that now governs every Falcon wizard going forward. Six rules. Each is enforced structurally by the folder layout + DI scope.

2.5.a — The Six Rules

  1. Rule 1 — State lives inside the component folder that owns it. No central services/state/ directory for state with a single component owner. Per-component signals stay co-located with their consumer.
  2. Rule 2 — Per-step signals folder. Every step inside a wizard has a <step>/signals/<step>.signals.ts file exporting an @Injectable() class with at least value / valid / dirty / revealed signals and a reset() method.
  3. Rule 3 — Wizard-wide signals. Cross-step state (open/close, eager catalogs, pending submit payload, generated password, dialog visibility) lives in <wizard>/signals/<wizard>.signals.ts. Same shape: @Injectable() class.
  4. Rule 4 — Provider hoisting at the wizard component. The wizard component declares providers: [...<WIZARD>_PROVIDERS] for its per-step services. The wizard-wide service is provided at the page level so it can be flipped open BEFORE the wizard mounts. Pristine state on every reopen comes for free from Angular DI lifecycle.
  5. Rule 5 — Reset method on each signal service. Each @Injectable() exposes a reset() method that re-seeds every signal from empty<FormName>() factories. Required for future "Start Over" buttons; not used by the wizard lifecycle (DI handles that).
  6. Rule 6 — Facade re-exports public surface. Page-level facade services (HierarchyPageStateService) re-export the public surface so consumers depend on the facade, not the internal split. This decouples future slice splits from consumer source.

2.5.b — Reference: the smallest signals file (Step 2, 39 LOC)

client-settings-step/signals/client-settings-step.signals.ts is the canonical minimal shape. Reproduced inline (header comments trimmed): 

import { Injectable, signal } from '@angular/core';

import { ClientSettingsFormValue, emptyClientSettings } from '../../models/models';

@Injectable()
export class ClientSettingsStepSignalsService {
  readonly value = signal<ClientSettingsFormValue>(emptyClientSettings());
  readonly valid = signal<boolean>(false);  // Wave 7 — starts invalid (null defaults)
  readonly dirty = signal<boolean>(false);
  readonly revealed = signal<boolean>(false);

  reset(): void {
    this.value.set(emptyClientSettings());
    this.valid.set(false);
    this.dirty.set(false);
    this.revealed.set(false);
  }
}

Note the absence of providedIn — that is intentional. The wizard component provides this service via ADD_CLIENT_WIZARD_PROVIDERS so its lifecycle tracks the wizard mount, not the application root.

2.6.a — Cross-step invariants

  • All form values use T | null scalar slots. The empty<Step>() factories return null for every scalar. Required-field validators treat null as { required: true }. The wire builder defensively coalesces null → '' | 0 | DefaultEnum for the few required wire slots so a slip-through still POSTs (but normal flow blocks Next before that path fires).
  • revealed propagates one direction only. Steps flip their own revealed signal on Next click via revealErrors(). The signal is read by the step template to switch invalid fields into state="error" visual mode. Validators don't change behavior — only the rendering does.
  • Eager data is only read, never refetched per step. The wizard's forkJoin on mount fires the 5 catalog calls (password, countries, cities, commchannels, apps) once. Per-step navigation reads from cached signals. DevTools Network confirms: open wizard → 5 calls at t=0 → Step 1 → 5 navigation cycles produce zero new XHR.
