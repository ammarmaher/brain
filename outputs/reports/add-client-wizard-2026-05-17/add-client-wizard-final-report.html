2. Original Problem Statement

The user wanted a working 5-step Add Client wizard with the following non-negotiable requirements, captured verbatim across Wave 4.2, Wave 5, Wave 6, and Wave 7 user messages:

Pillar What the user asked for
Backend integration All 6 Add Client APIs (lookups, async account-name check, generate-password, create-account) must fire live against the local Identity Gateway and System Gateway. ServiceOperationResult<T> envelope honored. Token-bearer auth required.
Proper validation Each step gets its own validations/validations.ts folder mirroring Add User wizard. Per-field inline messages, red borders on touch, Next disabled when invalid, stepper-rail dot paints red on Next click for invalid steps.
Business-validation toasts HTTP 200 + isSuccessful:false (business validation errors) must render as a top-right red toast showing the backend's exact errorMessages[0] string — not a centered confirmation popup, not a generic "Bad request" body.
Eager loading All 5 wizard APIs (generate-password, country lookup, city lookup, communication channels, applications) must fire in one parallel forkJoin on wizard mount. Navigation between steps must produce zero new XHR. Close + reopen fires a fresh batch.
Null-init defaults Every form field begins literally null. No '' for strings, no 0 for numbers, no 'normal' security default, no 'Account Owner' role default. Types widened to T | null; wire builder coalesces at the boundary.
Per-component signal architecture Each step's signals live INSIDE that step's component folder (<step>/signals/<step>.signals.ts). Wizard-wide signals live in add-client-wizard/signals/. No central services/state/ for state with a single component owner.
Pixel parity to React mockups The new Sending Credentials + Completion Success popups must match the React source-of-truth (C:\Falcon\Source_of_truth_theme\React\Falcon-Taha2\admin\addclient.jsx lines 680–767) — same 3-method-card layout, same illustrations, same auto-dismiss timer, same click-anywhere-to-dismiss behavior.
Falcon library only Zero native <button> / <input> / <dialog>. Every interactive element is a Falcon wrapper (<falcon-angular-*>). Missing component = extend the library, do not hand-roll.
Constraint of constraints: the user said "I will test" — so live verification was the user's responsibility, and the agent's job was to ship build-green + visually-correct code on every wave without autopiloting Chrome MCP E2E runs.

3. End-to-End Process Flow

This is the final shape of the user journey from the click that opens the wizard to the routing call that closes it. Every step below is annotated with the signals, APIs, and components that participate. Read top-to-bottom — the flow is strictly linear with two terminal branches at step 9 (success vs. error).

STEP 1 User clicks "Add Client" from Org Hierarchy
From the management-console org-hierarchy-page, the user opens the root-action menu and selects Add Client. HierarchyPageStateService (facade) routes to addClientState.openWizard(), which flips the addClientOpen signal false → true. The wizard mounts via Angular DI — providers are hoisted at AddClientWizardComponent via ADD_CLIENT_WIZARD_PROVIDERS, guaranteeing pristine state on every re-open.
STEP 2 Wizard mount fires forkJoin of 5 APIs in parallel
ngOnInit on AddClientWizardComponent calls clientService.prefetchWizardData() which forks 5 calls. catchError is applied per-inner so a single failure does not kill the batch.
  • POST /user/generate-password (Identity Gateway, port 8088) — returns one-shot strong password
  • GET /commerce/Lookup/{countryId} (System Gateway, port 7256) — country option list
  • GET /commerce/Lookup/{cityId} (System Gateway) — city option list
  • GET /commerce/CommunicationChannel (System Gateway) — available channels for Step 3 rows
  • GET /commerce/Application (System Gateway) — available applications for Step 4 rows
STEP 3 Results land in wizard-level signals (single source of truth for cached data)
The 5 responses unzip into 5 wizard signals stored in add-client-wizard.signals.ts:
  • eagerCountries — country lookup array
  • eagerCities — city lookup array
  • eagerCommChannels — communication channel rows for Step 3
  • eagerApps — application rows for Step 4
  • lastGeneratedPassword — pre-filled password for Step 5
Steps READ from these signals — they do not own them. On closeWizard() the signals are cleared so the next open fires a fresh batch.
STEP 4 Step 1 — Client Information
Country/city dropdowns bind to eagerCountries / eagerCities — no fresh XHR. All form fields start literally null (Wave 7 widened types to T | null across models.ts). The accountName field runs async uniqueness check via POST /commerce/Account/account-name-availability on debounceTime(300) from the value-change pipe — untracked(() => ...) wraps every signal.set inside the switchMap to prevent renderer freezes that Wave 4 originally hit.

Photo upload emits the canonical object shape: { extension: 'png', fileBase64String: '...' }, written into step1Value().info.profilePictureImageInfo. The <app-falcon-photo-uploader> component gained a pictureChange output in Wave 6 to surface this shape (backward-compatible with the existing photo data-URL model used for preview).
STEP 5 Steps 2, 3, 4, 5 — pure view + form (no new XHR)
Navigation between steps does NOT trigger network calls. Each step:
  • Step 2 — Client Settings: security mode + IP allowlist + 3 user/session limits — all null-init (Wave 7). Step starts isFormValid === false until user picks a security mode.
  • Step 3 — Communication Channels: reads eagerCommChannels into the shared <client-service-row-table> editor. Per-row priceType + priceValue with the new Saudi Riyal left-icon on the <falcon-angular-input-number>.
  • Step 4 — Applications: identical row-table component, fed from eagerApps. Same validation cascade.
  • Step 5 — Account Owner: form fields all null-init (no 'Account Owner' role default). Password field pre-filled from lastGeneratedPassword; eye toggle works even when input is readonly (Wave 4.2 library fix in falcon-password-tw.tsx).
STEP 6 Row-table validation cascade (Step 3 + 4)
When the user clicks Next on Step 3 or 4 with an invalid row, revealAllRowsErrors() runs. Wave 7 hardened this to fix an OnPush re-render bug — in addition to flipping touched signals, it now also calls this.rows.update((rs) => [...rs]) to force a new array reference on the data-table input. Without this spread, the OnPush <falcon-angular-data-table> child would retain stale cell renderers and the red borders would only appear after a manual dropdown click.

Touch keys (priceTypeTouched, priceValueTouched) are also defensively auto-set inside setPriceType() / setPriceValue() so the red state follows typing without needing a blur event. The stepper-rail dot's color binds to step.isFormValid(), so an invalid step paints red on Next click.
STEP 7 Save click on Step 5 → opens Sending Credentials popup
Clicking Save on Step 5 does NOT submit yet. Instead, the wizard signals service flips sendingCredentialsOpen.set(true), which mounts the new <falcon-angular-sending-credentials-dialog> component (library addition from Wave 5.1). The popup is fed:
  • ownerName, ownerEmail, ownerPhone from step5Value()
  • defaultDelivery — Email by default
The popup renders the 3 method cards (Email / SMS / Both) + the AO summary block + Cancel/Send buttons. Pixel parity to React source at addclient.jsx:680-749.
STEP 8 User picks Email/SMS/Both → maps to DeliveryMethod enum → POSTs create-account
The popup emits (send)="onSend('email'|'sms'|'both')". The wizard signals service maps the string to the canonical DeliveryMethod enum (libs/falcon/src/shared-types/lib/enums/globels.ts:97) — Email = 1, Sms = 2, Both = 3. Wave 6 corrected this; before Wave 6 the wire field was a string. buildCreateAccountWireRequest() in wire-builders.ts assembles the full payload — all 5 step states, photo objects, delivery method int, owner info — and the service issues:

POST /commerce/Node/create-account (System Gateway, bearer token forwarded).

While the call is in-flight, pendingCreate.set(true) drives a busy state on the popup's Send button.
STEP 9-A Success branch (HTTP 200 + isSuccessful:true)
The dispatcher's FALCON_HTTP_UI_CONFIG resolves the response as success — no rule fires. The wizard signals service:
  • Closes the Sending Credentials popup (sendingCredentialsOpen.set(false))
  • Opens the Completion Success popup (completionSuccessOpen.set(true))
  • Starts the 10s auto-dismiss timer (configurable via autoDismissMs)
The <falcon-angular-completion-success-dialog> renders the clipboard-with-checkmark illustration + title + subtitle. Click anywhere OR timer elapses → emits (closed). The wizard listens and calls router.navigate(['/admin-console/org-hierarchy-page'], { queryParams: { selectedNode: id } }) — returning to the org-hierarchy with the new client pre-selected.
STEP 9-B Business validation error branch (HTTP 200 + isSuccessful:false, OR 422)
Backend returns the success envelope with isSuccessful: false and an errorMessages array. The dispatcher's resolver routes this to the applicationError rule (Wave 4.2 addition to FalconHttpUiErrorBucket union). The rule:
  • Title from the rule's title field (i18n key or category default)
  • Subtitle = backend's errorMessages[0] via extractInBodyErrorDetail
  • Render mode: top-right toast (red, error intent), 5s auto-dismiss
Field-level errors map back to the originating step via FIELD_LEVEL_ERROR_MAP (e.g. VAL_010 → Step 1 accountName, VAL_023 → Step 5 ownerEmail). The toast appears in the host-shell's mounted <falcon-angular-notification-stack position="top-right">.
STEP 9-C Transport error branch (5xx, network failure)
Genuine transport failures (500, 502, network drop) still route through the existing FalconHttpErrorDialogService — a centered confirmation popup with retry. This path was unchanged in this session; the Wave 4.2 fix kept it intact while carving out the applicationError bucket for business validation specifically. The user can dismiss the popup and the wizard remains open with its filled-in state preserved.
Performance characteristic: the entire wizard session, from open to close, costs 5 parallel XHR on mount + 1 sequential POST on save. Zero per-step API chatter. Verified via DevTools Network panel: navigating Step 1 → 5 in any order produces zero new requests.

2.2 — State Architecture

The Add Client wizard runs on a three-layer DI cake: page → wizard → step. Each layer owns the state that survives at its own lifecycle. Provider hoisting at the wizard component guarantees that wizard-scoped step services are destroyed on close and recreated on reopen — no manual reset cascade is needed for pristine state.

2.2.a — The four-step layered model

  1. Page route (org-hierarchy-page.routes.ts) declares the HIERARCHY_PAGE_STATE_PROVIDERS aggregate. This aggregate registers the 5 surviving page-level slices AND the wizard-wide AddClientWizardSignalsService. Lifetime: as long as the page route is active.
  2. Facade HierarchyPageStateService (slim 338-LOC re-exporter) injects the 5 page slices and the wizard-wide signals service. It re-exports their public surface so existing consumers (page menu, settings tab, user-details page) compile against a single facade rather than 6 separate services.
  3. Wizard component (add-client-wizard.component.ts) declares providers: [...ADD_CLIENT_WIZARD_PROVIDERS] in its @Component decorator. This hoists the 5 per-step signal services into a wizard-scoped sub-injector. When the parent template's @if state.addClientOpen() falls, Angular destroys this sub-injector → all 5 step services drop with it.
  4. Per-step signal services live inside their step folders: <step>/signals/<step>.signals.ts. Each is a plain @Injectable() (no providedIn) exposing 4 signals — value, valid, dirty, revealed — plus a reset() method. The wizard binds [(value)]="state1.value" on each step via viewChild() refs.

2.2.c — Why this split?

Layer Scope Why this level?
Page slices (tree, users, drawer, settings, add-user) Page route Each spans multiple components on the page. No single owner. Lives as long as the operator is on Organization Hierarchy.
AddClientWizardSignalsService Page route The page menu sets addClientOpen.set(true) before the wizard component exists. The wizard then injects the SAME instance via DI walk-up. Also keeps the eager-loaded catalogs warm if the wizard closes + reopens within the same page session.
5 per-step signal services Wizard component (via providers) Wizard mount/unmount drives their lifecycle. Pristine state on every reopen without an explicit reset call — Angular's DI lifecycle does it for free. The optional reset() method exists for a future "Start Over" button mid-wizard.

2.5 — Per-Component Signals Doctrine (forward-applicable)

Wave 6.2 (Agent I) formalized the doctrine that now governs every Falcon wizard going forward. Six rules. Each is enforced structurally by the folder layout + DI scope.

2.5.a — The Six Rules

  1. Rule 1 — State lives inside the component folder that owns it. No central services/state/ directory for state with a single component owner. Per-component signals stay co-located with their consumer.
  2. Rule 2 — Per-step signals folder. Every step inside a wizard has a <step>/signals/<step>.signals.ts file exporting an @Injectable() class with at least value / valid / dirty / revealed signals and a reset() method.
  3. Rule 3 — Wizard-wide signals. Cross-step state (open/close, eager catalogs, pending submit payload, generated password, dialog visibility) lives in <wizard>/signals/<wizard>.signals.ts. Same shape: @Injectable() class.
  4. Rule 4 — Provider hoisting at the wizard component. The wizard component declares providers: [...<WIZARD>_PROVIDERS] for its per-step services. The wizard-wide service is provided at the page level so it can be flipped open BEFORE the wizard mounts. Pristine state on every reopen comes for free from Angular DI lifecycle.
  5. Rule 5 — Reset method on each signal service. Each @Injectable() exposes a reset() method that re-seeds every signal from empty<FormName>() factories. Required for future "Start Over" buttons; not used by the wizard lifecycle (DI handles that).
  6. Rule 6 — Facade re-exports public surface. Page-level facade services (HierarchyPageStateService) re-export the public surface so consumers depend on the facade, not the internal split. This decouples future slice splits from consumer source.

The user's second observation was the key diagnostic detail. The validation was wired correctly. The CSS classes were correct. The data was correct. But the row didn't paint red until something other than the validation reveal itself mutated the row data.

The bug, debugged in five steps
SYMPTOM
On Step 3, the user toggles a row visible, leaves priceType empty, and clicks Next. The step rail dot turns red (step validity is correctly false). The visible row's priceType dropdown and priceValue input do not paint red despite being invalid.
USER CLUE
After Next is clicked, the user opens the priceType dropdown and picks 'Fixed'. The dropdown closes. Now the priceValue input paints red — even though the user only touched the dropdown, not the input.
DIAGNOSIS
The row table is rendered via <falcon-angular-data-table>, which is ChangeDetectionStrategy.OnPush. The data input is [data]="rows()" — a signal-as-array. OnPush re-renders cells only when the rows array reference changes.

revealAllRowsErrors() flipped the touched signal but didn't mutate rows. The cells' [state] input is computed from the touched signal — but the data-table doesn't re-render those cells because its data reference is unchanged. The cells render the old [state]="default" from the previous tick.

When the user picked a price type from the dropdown, setPriceType(row, value) ran rows.update((rs) => rs.map(...)) — that produced a new array reference, the data-table re-rendered cells, and the previously-flipped touched values finally produced the red state.
CONFIRMATION
The user reproduced the bug consistently. Clicking a dropdown was the trigger to make the OTHER input (which the user hadn't touched) paint red. Classic OnPush + signal identity trap.
FIX
Two changes to client-service-row-table.component.ts:

1. revealAllRowsErrors() now forces a new array reference. After touched.set(...), it also does rows.update((rs) => [...rs]). Shallow spread = new array reference = data-table re-renders cells = previously-touched validity reflects.

2. setPriceType and setPriceValue defensively auto-set their corresponding touch keys. So when the user types into the input, the touched key flips reactively — red feedback follows typing without needing an explicit blur or a Next-click.

revealAllRowsErrors() {
  const visibleRows = this.rows().filter((r) => r.visible);
  const nextTouched = { ...this.touched() };
  for (const row of visibleRows) {
    nextTouched[`${row.id}.priceType`] = true;
    nextTouched[`${row.id}.priceValue`] = true;
  }
  this.touched.set(nextTouched);
  + // CRITICAL: force new array reference so OnPush <falcon-data-table>
  + // re-renders cells that depend on touched state.
  + this.rows.update((rs) => [...rs]);
}

setPriceType(row: ServiceRow, value: PriceType) {
  this.rows.update((rs) => rs.map((r) => r.id === row.id ? { ...r, priceType: value } : r));

M3

Set defaults instead of null (repeated 2x)

Severity: medium

What happened

Initial emptyClient*() factories used '' for strings, 0 for numbers, and kept security: 'normal' and ownerRole: 'Account Owner' as defaults. The user wanted everything truly null so the UI could reflect "operator hasn't picked yet" and validation could enforce a conscious choice. It took 2 user messages and 2 agent dispatches before I widened the types from T to T | null and updated every factory.

Root cause

Interpreted "make it null" as "use the empty representation that won't trip the form." That is form-engineer's autopilot — Angular Reactive Forms historically punishes null. But the user was talking about state truth: nothing should be in the model until the operator chooses it. Two different mental models collided, and I didn't recognize it the first time.

Impact

Two full agent dispatches: the first kept defaults, the second only updated factories. A third pass widened the types in models/models.ts. Roughly 40 minutes of back-and-forth. User had to repeat themselves twice.

Rule going forward

"Make it null" means literally null. The sequence is:

  1. Widen the form interface types in models/models.ts first (string → string | null, etc.)
  2. Update every empty*() factory to return all-null
  3. Update validators to handle null (most "required" rules already do — confirm)
  4. Update the wire builder to coalesce null → wire-acceptable value (?? '', ?? 0, etc.) at the boundary

How to spot this in the future

When the user says "null" — literally search the code for empty-string and zero defaults in form state. If you see name: '', that's the trigger.

M4

Used raw SVG string API instead of content projection

Severity: medium

What happened

Designed the FalconAngularInputNumberComponent icon API as [iconLeftSvg]="rawSvgString" — consumer passes a raw SVG string. User pushed back: "passing just the class for the icon… easy peasy." The redesign in Wave 7 replaced the input with iconLeft boolean + <ng-content select="[falcon-input-number-icon-left]">. Consumer drops in the real icon component as a child.

Root cause

Stencil's underlying falcon-input-number-tw has an iconLeftSvg prop (because Stencil cross-framework consumers can't easily do projection). I mirrored that into the Angular wrapper without thinking. Angular has a richer story — content projection — and that's what an Angular consumer wants.

Impact

API was wrong-shaped in Wave 6.1 + half of Wave 7. Redesign required: new booleanAttribute input, new ng-content slot, new docs in the consumer (client-service-row-table). Roughly 30 minutes.

Rule going forward

When the consumer pattern is "drop in any icon/badge/action component," use <ng-content> projection — NOT raw string inputs. The whole reason a component library exists is so consumers don't pass strings of SVG. Keep the Stencil string prop for non-Angular consumers; the Angular wrapper layers ng-content on top.

How to spot this in the future

If you find yourself typing @Input() iconLeftSvg: string or [innerHTML] binding in a wrapper, stop. The Angular wrapper exists to be more ergonomic than the Stencil base. Slot-based composition is the more ergonomic choice every time.

M5

Row-table validation didn't render on Next click

Severity: high

What happened

Wave 6.1 added revealAllRowsErrors() to flip every row's touched signal so red borders would appear when the operator hit Next without filling required fields. It didn't work. The user saw zero visual feedback on Next click. The red state only appeared after manually focusing-and-blurring a dropdown inside the row. Wave 7 diagnosed the real cause and fixed it.

Root cause

OnPush child + signal-array input + reference-stable mutation. <falcon-angular-data-table> is OnPush. Its [data] input binds to rows(). When revealAllRowsErrors() updated each row's touched signal, the rows signal array reference DID NOT change (touched is a per-row signal living inside the row object). OnPush + signal change detection schedules a re-render only when the bound signal's tracked dependencies change for the child. Mutating a row-internal signal doesn't count.

Impact

User-reported bug. Surfaced after Wave 6.1 had already shipped + claimed live verification. Wave 7 had to re-investigate + diagnose + fix. ~45 minutes plus erosion of "live verified" trust. This is the most consequential bug of the session.

Rule going forward

OnPush + signal-array: reference identity matters. When you change a tangential per-item state (touched, focus, validity, expansion) that the OnPush child depends on, you MUST force a new reference on the upstream array. Pattern: 

this.rows.update((rs) => [...rs]);  // spread to force new ref

The defensive fix in Wave 7 also auto-set the touched key in setPriceType/setPriceValue so red state followed typing without needing blur — that's a separate quality-of-life win, but the core rule is the array spread.

How to spot this in the future

Whenever you write a method that mutates per-row state in a row-table or any OnPush list view, ask: "would the parent array's reference change as a result?" If no, add a spread. When in doubt, spread. The cost is one allocation per call; the benefit is correctness.

M7

Stale Wave 4 popup vs Wave 4.2 toast confusion

Severity: low

What happened

In Wave 4, backend validation errors (HTTP 200 + isSuccessful:false) routed to the default rule in FALCON_HTTP_UI_CONFIG — a center popup. User wanted those as a top-right toast. I initially tried to bend the 4xx rule path to cover this, but those are different paths in the dispatcher: 4xx is for TRANSPORT errors; isSuccessful:false is application-layer.

Root cause

Conflated transport errors (HTTP 4xx/5xx, caught in the error handler arm of the observable) with application errors (HTTP 200 with a structured failure envelope, caught in the success arm via a "withMessages" hook). Impact

How to spot this in the future

When designing error UI for a new endpoint: ask whether the failure comes through the observable's error arm or its success-with-failure-envelope arm. If success-with-envelope, you need the application bucket. If error-arm, you're in the transport bucket.

Anti-Pattern Catalog

10 patterns that surfaced this session that should never appear in Falcon code again. For each: the bad shape, the good shape, why the bad shape is wrong. Use these as Grep targets during code review.

1. Raw SVG string component inputs

Bad
// Component
@Input() iconLeftSvg?: string;

// Template
<falcon-input-number
  [iconLeftSvg]="'<svg>...</svg>'">
</falcon-input-number>
Good
// Component
@Input({ transform: booleanAttribute })
  iconLeft = false;
// + <ng-content select="[falcon-input-number-icon-left]">

// Template
<falcon-input-number iconLeft>
  <falcon-angular-saudi-riyal-icon
    falcon-input-number-icon-left>
  </falcon-angular-saudi-riyal-icon>
</falcon-input-number>

Why bad: raw SVG strings bypass the type system, lose accessibility attributes, break tree-shaking (SVG bytes inline), and force consumers to do unsafe [innerHTML] binding. Content projection lets the consumer drop in a real component with its own bindings, ARIA labels, and styling.

2. OnPush child with [data]=signal() where signal mutates but reference doesn't

Bad
revealAllRowsErrors() {
  for (const row of this.rows()) {
    row.touched.priceType.set(true);
    row.touched.priceValue.set(true);
  }
  // Array ref unchanged — OnPush child won't refresh
}
Good
revealAllRowsErrors() {
  for (const row of this.rows()) {
    row.touched.priceType.set(true);
    row.touched.priceValue.set(true);
  }
  // Force new array reference for OnPush
  this.rows.update((rs) => [...rs]);
}

Why bad: OnPush + signal arrays require reference change to trigger re-render in the child. Mutating per-item state inside the array doesn't change the array's reference, so the OnPush child sees the same input and skips change detection. Spread the array to force a new reference whenever you change tangential per-item state.

3. signal.set() inside RxJS switchMap reading a signal-derived observable

Bad
toObservable(this.selectedNode).pipe(
  switchMap((node) => this.api.fetch(node)),
  tap((data) => {
    this.dataSignal.set(data);
    // Angular flags: write-in-tracked-context
    // Renderer may freeze
  })
).subscribe();
Good
toObservable(this.selectedNode).pipe(
  switchMap((node) => this.api.fetch(node)),
  tap((data) => {
    untracked(() => this.dataSignal.set(data));
  })
).subscribe();

Why bad: when a RxJS pipe is fed by toObservable(signal) the downstream callbacks may run inside Angular's tracked context. Calling signal.set() there is "write-in-tracked-context" and can produce circular update warnings or — worse — silently freeze the renderer (the Wave 4 freeze bug). Wrapping .set() in untracked(() => …) tells Angular this write is not part of the reactivity graph and is safe.

4. @Input() flag = false for bare-attribute use

Bad
// Component
@Input() iconLeft = false;

// Template
<falcon-input-number iconLeft>...
// ERROR: '""' is not assignable to 'boolean'
Good
import { booleanAttribute } from '@angular/core';

@Input({ transform: booleanAttribute })
  iconLeft = false;

// Template
<falcon-input-number iconLeft>...
// OK — bare attribute coerced to true

Why bad: Angular's strict template type-checker treats bare attributes as empty strings. booleanAttribute is the canonical coercer: "" → true, "false" → false, anything else → true. Same family includes numberAttribute for numeric inputs.

5. Initializing form state with display defaults instead of null

Bad

  return {
    authority: 'Government',
    security: 'normal',
    userLimits: 100,
    // UI shows preset values — operator
    // never made a conscious choice
  };
}
Good
// Widen types in models/models.ts first
authority: AuthorityType | null;
security: SecurityLevel | null;
userLimits: number | null;

emptyClientSettings(): ClientSettings {
  return {
    authority: null,
    security: null,
    userLimits: null,
  };
}

Why bad: defaults masquerade as choices. The operator hits Next without ever seeing the field, but the form ships preset values that look like decisions. Required validation also can't enforce a conscious pick. Null = "operator hasn't chosen yet"; defaults silently bypass that signal. Coalesce at the wire-builder boundary, not in form state.

Why bad: HTTP 200 + isSuccessful:false is an application-layer error, not a transport error and not "everything else." Routing it through default conflates business validation with unexpected failures — the user sees a center dialog for what should be inline form feedback. Add the applicationError bucket and route it deliberately.

Standing Rules Codified

The 10 operational rules and 6 architectural doctrines from the session memory file. These are the durable artifacts — what every future Ammar session that touches a Falcon wizard should apply.

Operational rules (10)

  1. "Make it null" means literally null — widen types first
    Any time the user asks for null defaults, or whenever you design form state from scratch. Widen T → T | null in models/models.ts BEFORE updating factories.
  2. OnPush + signal-array: reference identity matters
    When you change a tangential per-item state (touched, focus, validity) that an OnPush child depends on. Force a new array reference with signal.update(arr => [...arr]).
  3. No raw SVG strings in component APIs — use ng-content projection
    Designing any Falcon wrapper component that accepts an icon, badge, or action slot. Use <ng-content select="[slot-name]">, not @Input() iconSvg: string.
  4. Always grep libs/ for existing enums/icons/components before inventing
    Whenever you're about to type an inline SVG, a string-literal union, or a new component. Grep: libs/falcon/src/shared-types/lib/enums/, libs/falcon/src/shared-ui/lib/components/, libs/falcon-ui-core/src/angular-wrapper/components/.
  5. Test runner must be sanity-tested before writing 30+ specs
    In any workspace where vitest hasn't been run in > 1 week. Write a single sanity.spec.ts with expect(1+1).toBe(2). Run it. Confirm green. Then commit to the real spec suite.
  6. untracked() for signal.set inside RxJS pipes that read signals via toObservable
    Any RxJS pipeline fed by toObservable(signal) where a downstream callback calls .set() on another signal. Wrap the .set() in untracked(() => …) to escape tracked context.
  7. Load Brain SK CLAUDE.md + the page-specific playbook before starting
    Session start for any Falcon page-level user action. The 8 verification questions in IMPLEMENTATION_KNOWLEDGE_MAP.md are the gate — you haven't loaded enough until you can answer all 8 with file citations.
  8. @Input({ transform: booleanAttribute }) for bare-attribute boolean inputs
    Any boolean input you expect consumers to use as a bare HTML attribute (<comp flag> rather than [flag]="true"). Import booleanAttribute from @angular/core.
  9. Backend validation errors (HTTP 200 + isSuccessful:false) → applicationError rule
    Designing error UI for any new endpoint. If failures come through the observable's success arm with a failure envelope, you need the 'applicationError' bucket — NOT 4xx, NOT default.
  10. "I will test" → don't autopilot live verification
    Before dispatching an agent for QA or running a Chrome MCP session. Scan the last 3 user messages for hard constraints. "I will test" is one of them.

Architectural doctrines (6)

A State lives next to its consumer (per-component signals folder)

Per-component state goes inside the component folder at signals/. No central services/state/ for state with a single component owner. Page-wide state spanning multiple unrelated components is the exception.

B Provider hoisting at the wizard component level (pristine state via DI lifecycle)

Per-step signal services are @Injectable() (no providedIn). They get provided once at the wizard component via providers: [...ADD_CLIENT_WIZARD_PROVIDERS]. Each wizard mount creates fresh instances; no manual reset cascade.

C Eager loading on wizard mount (one forkJoin, steps consume from cache)

Every API dependency the wizard needs across its steps fires in one forkJoin on mount. Steps read from cached signals. Step navigation fires zero new XHRs. Cache resets on wizard close.

D Content projection > raw-string inputs (for icons, badges, actions)

Component slots use <ng-content select="[slot-name]">. Consumer drops in a real component with its own bindings. Never [innerHTML], never SVG strings.

E OnPush + signal arrays — force new reference on tangential state change

When you change a per-item state (touched, focus) that an OnPush child depends on, the parent array reference must change too. Spread is the canonical fix: signal.update(arr => [...arr]).

F Pure helpers for testability — extract routing/extraction logic from services

Logic that doesn't need Angular DI lives in standalone .ts files (e.g. falcon-http-ui-routing.ts). Services delegate. Tests hit the helper directly without TestBed bootstrap. Faster, more focused, no Angular zone or DI noise.
