## 5. API SPEC (as stated in [PRD-V5 §API, L447–496])

Purpose: system-to-system parity with the UI for the "client (Normal user & in future only system user)" [L448–449].

### 5.1 BSA Send-Transaction API
| Field / capability | Constraint (PRD) | Source |
|---|---|---|
| AuthN + AuthZ | required for the calling user | L451 |
| commchannel / sending method | "Whatsapp or Voice" | L452 |
| SenderName / SenderID | WA phone number or voice phone number | L453 |
| Message body | WhatsApp template ID or Voice IVR ID; "our autogenerated ID, or the Reference ID linked to that template while its creation" | L454–455 |
| Contact group | **"ONLY one contact group per request"** — deliberate narrowing vs UI's one-or-multiple CGs (BR-BSA-30); destination column passed as value of key "Destination/Recipient"; variable map as Key = exact template/IVR variable name, Value = CG column name | L456–459 |
| Manual recipients | "a list of recipients 'phone numbers'"; per recipient: Key = exact variable name, Value = variable value. UI's max-3 not restated for API (ABSENT) | L460–461 |
| Duplication behaviour | allow or not | L462–463 |
| Send date | omitted ⇒ now; if given ⇒ "should be greater than now and datetime format" | L464–466 |
| Errors | "Detailed and meaningful errors if there is anything not correct or rejected" | L467 |

### 5.2 Skeleton API — Retrieve Templates
AuthN/AuthZ [L469]; caller specifies commchannel (whatsapp or Voice) [L470]; returns only own/shared AND Approved templates [L471]. Per-template JSON: Template type (WA: Authentication/Utility/Marketing; Voice: Dynamic/Static) [L473], Template Name [L474], Language (only WA, "if exist") [L475], Template ID (autogenerated) [L476], Reference ID [L477], Variable list [L478].

### 5.3 Skeleton API — Retrieve Contact Groups
AuthN/AuthZ [L480]; returns only own/shared AND active "not deleted" CGs [L481]. Per-CG JSON: CG name [L483], CG ID [L484], Reference ID [L485], "Columns name in each template, their final shape" [L486] ([INFERRED] "template" here means contact group — wording slip).

### 5.4 Skeleton API — Retrieve SenderName/SenderID
AuthN/AuthZ [L488]; returns JSON list of { Commchannel, list of SenderNames/SenderIDs under that commchannel } [L489–491].

### 5.5 Near-future (explicitly deferred) [L492–496]
1. App configuration for who manages statuses and callback. 2. Status-inquiry APIs per transaction and per recipient. 3. Balance-inquiry API ("for the Skeleton not for the app"). 4. Allow/"now allow" (sic — not allow) partial processing on insufficient balance.

Key discrepancy to carry into implementation: UI supports multiple CGs per transaction [L56], API supports exactly one CG per request [L457]; API callers wanting multi-CG behavior must issue multiple requests ([INFERRED]), which changes dedup scope: UI dedup is cross-CG within one transaction [L85], multiple API calls would each be separate transactions.
