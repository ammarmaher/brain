# Cache Bloat Root Cause Analysis — `falcon-web-platform-ui`

**Date:** 2026-05-15
**Workspace:** `C:\Falcon\Falcon\falcon-web-platform-ui`
**Total regeneratable footprint at inspection:** ~28.7 GB
**Verdict:** ~21 GB of this is **bloat**, not normal — caused by three concrete bugs + missing size caps. Each one is independently fixable in <30 minutes.

---

## 1. Executive Summary

The frontend workspace is generating roughly **5× more cache than a healthy Nx + Angular monorepo should**. The bulk is not "natural" cache — it's the same builds being re-cached over and over because of a misconfigured Nx target, plus no eviction policy on either the Angular webpack cache or the Nx local cache.

**Healthy expectation for this workspace:** ~3–5 GB total (node_modules + a few GB of Angular cache + ~500 MB Nx cache).
**Actual:** 28.7 GB.
**Avoidable bloat:** ~21 GB (Angular cache: ~17 GB excess, Nx cache: ~7 GB excess, ~85% of which is one library's build output cached 90+ times).

## 3. What Each Folder Is And Whether It Should Exist

### ✅ Should exist (and IS normal)
| Folder | Why it exists | Best practice |
|---|---|---|
| `node_modules/` | npm dependency tree | Keep. Wipe only on dep changes / fresh install. |
| `dist/` | Final build artifacts | Regenerated per build. Gitignored ✓. |
| `libs/*/dist/` | Per-library build output | Regenerated. Gitignored ✓. |

### ⚠️ Should exist BUT must be capped
| Folder | Why it exists | What's wrong |
|---|---|---|
| `.angular/cache/` | Angular CLI's webpack persistent cache — makes incremental builds ~10× faster | **Unbounded by default.** No `cache.maxAge`, no `maxMemoryGenerations`. Webpack keeps ALL old packs. |
| `.nx/cache/` | Nx caches each task's output, keyed by input hash. Cache hit = no rebuild. | **No size limit.** 195 entries; many duplicates of the same library output because input hash changes every build (Bug #1 below). |
| `.angular/cache/babel-webpack` | Babel-loader output cache | Grows with code volume. Capped if you cap Angular cache. |

### 🗑️ Should NOT exist in this state
| Folder/file | Why it's wrong |
|---|---|
| `.dev-serve.log`, `static-*.log` | Dev-server output logs checked into the repo root. Should be in `tmp/` or `.gitignore`d (the static logs are not currently ignored). |
| `.vitepress/cache/` | VitePress dev artifacts inside the workspace root — fine, but should be in a more isolated location. |

### 🔴 Auto-generated source files (the smoking gun — see Bug #1)
These exist on disk and are gitignored — but they're regenerated by `nx build` every run, which causes the cache thrash:

| File | mtime | Generator |
|---|---|---|
| `libs/falcon-ui-core/.graceful-fs-boot.cjs` | 22:58:30 today | npm install / build.cjs |
| `libs/falcon-ui-core/loader/index.d.ts` | 22:59:15 today | Stencil build |
| `libs/falcon-ui-react/src/components.ts` | 22:59:15 today | `@stencil/react-output-target` |
| `libs/falcon-ui-vue/src/index.ts` | 22:59:16 today | `@stencil/vue-output-target` |

| `libs/falcon-studio/src/lib/registry/component-tokens.generated.ts` | 22:58:22 today | token generator |

Every one of these files lives **inside** a project root that has `cache: true` on its build target. They are gitignored, but **Nx hashes them as inputs anyway** because the default input glob is `{projectRoot}/**/*`. Result: cache miss every build.

## 4. Root Causes (3 bugs, ranked by impact)

### 🔴 Root Cause #1 — Build outputs feed back into the input hash (`cache thrash`)

**Location:** [libs/falcon-ui-core/project.json:33](Falcon/falcon-web-platform-ui/libs/falcon-ui-core/project.json:33)

```jsonc
"build": {
  "executor": "nx:run-commands",
  "dependsOn": ["install"],
  "options": { "command": "node build.cjs", "cwd": "libs/falcon-ui-core" },
  "outputs": ["{projectRoot}/dist", "{projectRoot}/loader", "{projectRoot}/www"],
  "cache": true                              // ← cache enabled
  // ← no `inputs` declared — falls back to default = "{projectRoot}/**/*"
}
```

**Why it's broken:**
1. `cache: true` tells Nx to hash all `inputs` and store the build output under that hash.
2. No `inputs` are declared → Nx uses the `default` namedInput: `"{projectRoot}/**/*"`.
3. The build **writes** `loader/index.d.ts` and `.graceful-fs-boot.cjs` INTO `{projectRoot}` — so they're part of `{projectRoot}/**/*` on the next build.
4. Next build: input hash differs (because `loader/index.d.ts` was just modified) → cache miss → new cache entry created (~98 MB).
5. **The cache never hits.** Every single `nx build falcon-ui-core` creates a new 98 MB cache entry.

**Evidence in the cache:**
- 90+ entries in `.nx/cache/*/libs/falcon-ui-core/dist` (each ~95–98 MB)
- 4 entries in `.nx/cache/*/libs/falcon-ui-core/node_modules` (each ~70–87 MB) — the `install` target has the same bug
- All created today, in spurts every few minutes during your dev session

**Impact:** ~85% of the 7.7 GB in `.nx/cache` is duplicate snapshots of one library's output.

### 🔴 Root Cause #2 — No size cap on `.angular/cache` (webpack persistent cache)

**Location:** No `angular.json` cache config; no custom `cache` block in [apps/admin-console/webpack.config.ts](Falcon/falcon-web-platform-ui/apps/admin-console/webpack.config.ts) etc.

**Why it's broken:**
1. Angular CLI delegates to webpack 5's persistent cache (`cache: { type: 'filesystem' }`).
2. **Default:** webpack keeps cache packs for `maxAge: 5184000000 ms` (~60 days) and never auto-evicts based on size.
3. Each material dependency-graph change creates a NEW pack — old ones stay until they age out.
4. With 3 apps × heavy dev iteration today, you accumulated 34 pack files ranging 105 MB to **1.22 GB each**.

**Evidence:**
```

  488 MB  7c11a...
  490 MB  7d29d...
  733 MB  a2e42...
1,220 MB  a3aa5...   ← single pack > 1 GB
1,046 MB  d09e7...
  798 MB  a8c48...
  723 MB  f486b...
  697 MB  e3216...
```

**Impact:** 13.1 GB of webpack pack files. Realistic warm cache would be 1–3 GB.

### 🔴 Root Cause #3 — No size cap on `.nx/cache` + `pre-*` npm hooks force rebuilds

**Location:** [nx.json](Falcon/falcon-web-platform-ui/nx.json) — no `cacheDirectory.maxSize` or eviction policy. [package.json:8-21](Falcon/falcon-web-platform-ui/package.json:8) — every `npm start` / `npm run serve:*` / `npm run build:*` runs `prestart`/`preserve:*`/`prebuild:*` that triggers `npm run build:libs` first.

```json
// package.json (relevant scripts)
"build:libs": "cross-env NX_NO_CLOUD=true nx run-many --target=build --projects=falcon-ui-tokens,falcon-ui-core,falcon-studio",
"prestart": "npm run build:libs",
"preserve:admin": "npm run build:libs",
"preserve:management": "npm run build:libs",
"prebuild:host-shell:prod": "npm run build:libs",
"prebuild:admin-console:prod": "npm run build:libs",
"prebuild:management-console:prod": "npm run build:libs",
```

**Why it's broken:**
1. Every npm dev command rebuilds 3 libs.
2. Combined with Bug #1, every rebuild = cache miss = new 100 MB cache entry.
3. Nx has no built-in size-based eviction. There is **no `nx clean` script in package.json** — `nx reset` exists but it's never invoked.
4. Nx Cloud is explicitly disabled (`neverConnectToCloud: true`, `NX_NO_CLOUD=true`) — local cache is the only cache.

**Impact:** 195 cache entries accumulated in ~12 hours. Realistic count for a 3-app workspace: 20–50.

## 6. Recommended Fixes (in priority order)

### 🥇 Fix #1 — Declare proper `inputs` on `falcon-ui-core` build (kills 85% of `.nx/cache` bloat)

In [libs/falcon-ui-core/project.json](Falcon/falcon-web-platform-ui/libs/falcon-ui-core/project.json), add explicit inputs that **exclude the build's own outputs**:

```jsonc
"build": {
  "executor": "nx:run-commands",
  "dependsOn": ["install"],
  "options": { "command": "node build.cjs", "cwd": "libs/falcon-ui-core" },
  "outputs": ["{projectRoot}/dist", "{projectRoot}/loader", "{projectRoot}/www"],
  "cache": true,
  "inputs": [
    "{projectRoot}/src/**/*",
    "{projectRoot}/stencil.config.ts",
    "{projectRoot}/build.cjs",
    "{projectRoot}/package.json",
    "{projectRoot}/tsconfig.json",
    "!{projectRoot}/dist/**/*",
    "!{projectRoot}/loader/**/*",
    "!{projectRoot}/www/**/*",
    "!{projectRoot}/.graceful-fs-boot.cjs",
    "!{projectRoot}/node_modules/**/*"
  ]
}
```

Or, cleaner — define a `stencil-build` namedInput in `nx.json` and reuse it across all Stencil libs.

**Impact:** Future builds with no source changes → cache HIT → reuses one 98 MB entry forever instead of creating a new one each time.

### 🥈 Fix #2 — Cap Angular webpack cache size (kills ~10 GB)

In each app's webpack config (e.g. [apps/admin-console/webpack.config.ts](Falcon/falcon-web-platform-ui/apps/admin-console/webpack.config.ts)), set:

```ts
export default (config) => {
  config.cache = {
    ...config.cache,
    type: 'filesystem',
    maxAge: 1000 * 60 * 60 * 24 * 7,        // 7 days, not 60
    maxMemoryGenerations: 1,                  // don't keep multiple in-mem generations
    compression: 'gzip'                       // optional — smaller packs at small CPU cost
  };
  return config;
};
```

Or — even simpler — set on the root build's `cli.cache` in `angular.json`:

```jsonc
// at repo root, create angular.json with:
{
  "version": 1,
  "cli": {
    "cache": {
      "enabled": true,
      "environment": "all",
      "path": ".angular/cache"
    },
    "schematicCollections": ["@nx/angular"]
  }
}
```

Then add an npm script that prunes packs older than 7 days.

### 🥉 Fix #3 — Add `clean` scripts and a periodic prune

In [package.json](Falcon/falcon-web-platform-ui/package.json) add:

```json
"clean": "npx rimraf dist tmp coverage",
"clean:cache": "npx nx reset && npx rimraf .angular/cache .vitepress/cache",
"clean:all": "npm run clean && npm run clean:cache && npx rimraf node_modules libs/*/node_modules",
"fresh": "npm run clean:all && npm install"
```

Now a fresh start is one command: `npm run fresh`.

### Fix #4 — Stop caching `install` target

The `install` target in `falcon-ui-core/project.json` shouldn't have `cache: true`. Caching a `node_modules` directory is fragile (paths inside often contain absolute paths). Remove:

```diff
  "install": {
    "executor": "nx:run-commands",
    "options": { "command": "npm install ...", "cwd": "libs/falcon-ui-core" },
-   "outputs": ["{projectRoot}/node_modules"],
-   "cache": true,
-   "inputs": [
-     "{projectRoot}/package.json",
-     "{projectRoot}/package-lock.json"
-   ]
  }
```

Use a simple `depends-on` check instead, or run install once via root postinstall.

### Fix #5 — Drop `prestart`/`preserve:*` rebuild loop where Nx already handles it

`nx serve admin-console` with `dependsOn: ["^build"]` (already set in `nx.json`) will auto-build dependent libs. The `preserve:admin: npm run build:libs` step is **redundant** AND it forces a rebuild bypassing Nx's affected detection.

Remove the `pre*` hooks; let Nx's dep graph handle it. CI can keep them as belt-and-suspenders.

### Fix #6 — Stencil output target redirection

Configure `@stencil/react-output-target` and `@stencil/vue-output-target` to write into a `.generated/` subdir, not under `src/`:

```ts
// stencil.config.ts
reactOutputTarget({
  outDir: '../falcon-ui-react/.generated',   // not src/
  componentCorePackage: '@falcon/ui-core'
})
```

Then in `falcon-ui-react/project.json`, add the generated dir to outputs and exclude from inputs.

### Fix #7 — Add missing `.gitignore` entries

```gitignore
# logs
.dev-serve.log
static-*.log
build-*.log

# auto-generated (already partially listed, complete it)
libs/falcon-ui-react/.generated/
libs/falcon-ui-vue/.generated/
```

## 8. Decision Point — Where to Go From Here

You paused the deletion. Three options:

**A) Just resume the delete (kicks the can).** You'll be back here in ~2 weeks of dev work. Picks no fights but solves nothing. ~28 GB freed, but cache grows back unbounded.

**B) Fix root causes first, then delete (recommended).**
   1. Apply Fix #1 (inputs on falcon-ui-core) — ~10 min, biggest win.
   2. Apply Fix #3 (clean scripts) — ~5 min.
   3. Apply Fix #2 (webpack cache.maxAge) — ~15 min.
   4. Then run `npm run clean:all` and `npm install`.
   5. File Fix #4–7 as separate small PRs.

**C) Delete now, file all fixes as PRs.** Fastest path to a usable disk. Fixes land in the next few days.

My recommendation is **B**: the inputs fix alone (Root Cause #1) is a 10-minute change that prevents the same 7+ GB pile from rebuilding tomorrow. Combine with the clean scripts and you have a sustainable workspace.

### Why "fresh start" got you here
You weren't doing anything wrong. The default Nx behavior + the missing `inputs` declaration + the missing webpack `maxAge` collude to produce unbounded growth. Without one of those three guard rails, any active dev workspace will hit 20–30 GB within a few weeks of iteration. This is a configuration debt, not a usage problem.
