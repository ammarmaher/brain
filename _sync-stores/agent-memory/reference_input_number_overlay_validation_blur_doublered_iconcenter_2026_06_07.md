# `falcon-angular-input-number` validation rendering — 3 reusable root causes + fixes (2026-06-07, claude)

Surfaced fixing the admin Add-Contract wizard **Step-1 Value (committedValue)** field + the rate-card Price Value. All FE-only, both apps build green, NO commits. The input-number is used overlay-style in contracts (﷼ prefix + SAR suffix as absolute siblings) — these 3 patterns recur on every such field.

## 1. No red on blur — non-CVA input-number consumers had NO public blur hook
`[CODE] libs/falcon-ui-core/src/angular-wrapper/components/falcon-input-number/falcon-input-number.component.ts` consumed the Stencil `(falcon-blur)` **internally only** (`handleBlur()` → `this.onTouched()`) and **never re-emitted a public `@Output`** — unlike the date-picker wrapper which exposes `(falconBlur)`. A field bound via standalone `[ngModel]` + `(valueChange)` (NOT `formControlName`/CVA — e.g. the contracts reactive form patched imperatively via `onInfoFieldChange`→`setValue`+`markAsDirty`) therefore had no way to mark its reactive control **touched** on blur. The error-show gate is `revealStep1Errors() || control.touched` (`contract-information-step.component.ts` `infoFieldHasError`), so clicking in/out of the empty required Value never flagged red until **Next** fired `revealErrors()`. **FIX (shared, additive):** added `@Output() falconBlur = new EventEmitter<void>()` to the wrapper + `this.falconBlur.emit()` in `handleBlur()`; wire `(falconBlur)="onInfoFieldBlur('committedValue')"` on the field. Purely additive — no existing consumer binds it. Wrapper convention: plain `falcon-angular-input` exposes `@Output() blur`; date-picker + (now) input-number expose `@Output() falconBlur`.

## 2. Double red background — `[state]="error"` ALREADY paints the wrapper red
`[state]="error"` makes `falconInputWrapperClasses` (`[CODE] libs/falcon-ui-core/src/tailwind/input-tailwind-classes.ts:112-120`) apply `bg-[var(--falcon-input-bg-error)]` (red-50) to the control-wrapper (the `.relative ${wrapperClasses}` div in `falcon-input-tw`). The inner `<input>` is `bg-transparent` (`falconInputControlClasses`), so the wrapper red shows through. Adding `!bg-falcon-red-100` on the input via `inputClass`/`inputExtraClass` STACKS a 2nd red (red-100 over red-50, inset by padding → a lighter outer band + darker inner) = the "dropped twice" look. **RULE (universal — no exceptions): error background = `[state]="error"` ONLY; NEVER add `!bg-falcon-red-100` on the input.** Fixed in: rate-card `priceValueInputClass()` (icon-padding only); BOTH wallet `wbm-balance-transfer-drawer.component.ts` `amountInputClass` (admin + mgmt — dropped the `overBalance() ? '!bg-falcon-red-100'` branch). ⚠️ The wallet drawer was a MIS-DESIGNED "exception": its `wallet-balance-management.component.ts` orchestrator overrides only error border/shadow/ring (`--falcon-input-border-color-error`/`-shadow-error`/`-ring-color-error` → `--falcon-wallet-*`) NOT `--falcon-input-bg-error`, and its `rootClass="!bg-[var(--falcon-wallet-surface)]..."` is **DEAD** — `@Prop rootClass` is declared in `falcon-input-number-tw.tsx:52` but NEVER referenced (the 2026-05-17 tag-switcher refactor dropped it; `falcon-input-tw` has no rootClass). The original design assumed rootClass forced the wrapper to wallet-surface (killing the wrapper red so only the input red-100 showed); with rootClass dead the wrapper red-50 leaks → double. Fix = drop the input red, keep the standard red-50 wrapper fill + wallet border/ring.

## 3. ﷼/SAR overlay icon DROPS to the bottom on error — `[errorMessage]` grows the centering wrapper
The ﷼ (left) + SAR (right) are absolute overlays centered with `top-1/2 -translate-y-1/2` against the field's `.relative` wrapper, which is supposed to wrap **only the control** (the label is already EXTRACTED to a sibling `<span>` ABOVE for exactly this reason). BUT the field still passed **`[errorMessage]`** to the input-number → the Stencil component renders the error `<p class="falcon-input-error">` **INSIDE** the wrapper, below the input row. On error the wrapper grows from input-height to `input + message`, so `top-1/2` becomes the center of the taller box → ﷼/SAR drop to the input bottom. (No error → no message → centered fine, so it only broke after validation fired.) **FIX = the proven wallet-drawer pattern:** never pass `[errorMessage]` on an overlay-centered input-number; **remove it** and render the error as an EXTRACTED sibling `<p data-falcon-input role="alert">` BELOW the `.relative`, reproducing `.falcon-input-error` token-for-token (`--falcon-input-error-*`: margin-top + inline padding + xxs/medium/red, line-height). The `data-falcon-input` marker is MANDATORY — `--falcon-input-error-*` (and `--falcon-input-label-*`) tokens are declared only inside `:where(falcon-input, falcon-input-tw, falcon-angular-input, .falcon-input, [data-falcon-input], …)` in `libs/falcon-ui-tokens/src/components/input.tokens.css`; without the marker the extracted node sits outside scope and renders at browser defaults. **General principle:** an overlay-centered input-number must keep its `.relative` wrapper = control-row only; BOTH label (above) and error (below) live as extracted siblings OUTSIDE it.
