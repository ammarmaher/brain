**Symptom:** Logged into host-shell (`localhost:4200`), clicking Organization Hierarchy / Permissions / Wallet / CommChannels / Marketplace / Contracts (all **admin-console remote** routes) → console shows `Failed to fetch dynamically imported module: http://localhost:4204/remoteEntry.mjs` + `504 (Gateway Timeout)` on `styles.css`. "Main Items" (Dashboard, Contact Groups, Templates) keep working because they live in the host itself. User reports "didn't change anything / worked before" — and that's TRUE: it's a dev-server runtime problem, not code or MF config.

**ROOT CAUSE (2026-05-31, RUNTIME-VERIFIED):** TWO concurrent `nx serve host-shell` instances were running — one from IDE `[CODE] .claude/launch.json:13` (`...serve host-shell --port 4200 --host 127.0.0.1 --skip-nx-cache`) AND one from `npm start` (`package.json start` = `nx serve host-shell --configuration=development`). host-shell serve = `@nx/angular:module-federation-dev-server` with `devRemotes:[]` → it serves admin-console/management-console as **STATIC remotes behind an nx proxy on :4204/:4301** (built once into `dist/apps`, served by lightweight `http-server`). Two stacks fought over ports (one bound `::1`, one `127.0.0.1`) + RAM; the static-remote proxy on :4204 began returning **504/404** for the large dev bundles (`remoteEntry.mjs` ~8MB, `styles.css` ~8.9MB). Aggravator: machine is RAM-tight (32GB; WebStorm ~3GB, Chrome ~3GB, Docker/WSL vmmemWSL ~2-3GB, Claude…).

**FIX (verified):** kill ALL Falcon node dev procs (match cmdline `nx\.js serve|run-executor|http-server dist|daemon.server.start`; PRESERVE WebStorm `tailwindcss-language-server`/`nxls` + `gitnexus` MCP), then start exactly ONE `nx serve host-shell --host 127.0.0.1`. Verify: `curl` 4200/ + 4204/remoteEntry.mjs + 4301/remoteEntry.mjs + 4204/styles.css all = **200**. Browser must HARD-refresh (Ctrl+Shift+R) — old 504 is client-cached.

**KEY GOTCHAS:**
- **Do NOT use `--devRemotes=admin-console,management-console`** to fix this — that runs 3 LIVE webpack dev servers, drove free RAM to 0.7GB and **OOM-crashed** the host build (`FATAL ERROR: Reached heap limit`, exit 134). The static-remote serve (plain `nx serve host-shell`) is the memory-light path: remotes become ~38MB http-servers, only the host keeps a heavy webpack server.
- **`--skip-nx-cache` is NOT the cause.** It only lives in `.claude/launch.json:13`. It forces a full from-scratch rebuild of host + both static remotes every launch (slow + memory-heavy, the reason a duplicate tipped over) — but functionally correct (added to avoid serving STALE cached MF remote bytes). **User chose 2026-05-31 to REMOVE it** from `.claude/launch.json:13` for lighter/faster restarts (cache reused; `nx reset` = occasional stale-buster). launch.json was otherwise clean/valid (single host-shell entry — no duplicate).
- The full `nx serve host-shell` build runs a dependency chain (`falcon-theme:generate-tokens-ts` → `falcon-ui-tokens:build-token-registry` → `falcon-ui-core` Stencil build ~1min → 3 Angular apps) — cold build is several minutes with long QUIET phases between tasks; do NOT misread an idle-CPU sample as a deadlock (I did, twice). Confirm progress via CPU delta over 10s, not a single sample.
- `nx reset` can fail `EBUSY` on `.nx/workspace-data/*.db` if the daemon/any nx proc is still alive — kill them first.
- Ports: host-shell 4200, admin-console **4204**, management-console **4301** (per `.claude/launch.json` + `apps/host-shell/src/assets/module-federation.manifest.json`). Builds OK = no compile errors in admin-console (3 builds exit 0); 40+ Stencil errors standing-truth did NOT block these.

**RECURRENCE RULE:** never run `npm start` AND the IDE launch.json host-shell at the same time — pick ONE. **CONFIRMED RECURRING 2026-05-31:** during the fix an `npm start` kept auto-relaunching (proc tree `powershell -NoProfile → npm start → nx serve host-shell`, `package.json start = nx serve host-shell --configuration=development`) and split-brained with the IDE/other server — host on :4200 owned by one PID, remotes :4204/:4301 by another → admin remote proxy 504. Told user to find the auto-launcher (WebStorm run-on-startup / a terminal tab / task runner) and disable one. **Second failure mode found:** a STALE nx daemon holds `.nx/workspace-data/<uuid>-v2.db` → `nx reset` fails `EBUSY` AND fresh `nx serve` dies with `NX Remote failed to start` (build log at `.nx/workspace-data/<ts>-build.log`). Fix: kill the daemon proc (`daemon.server.start` in cmdline) THEN `Remove-Item` the locked `*.db` directly, then serve. **GREEN END-STATE (verified):** single `nx serve host-shell --port 4200 --host 127.0.0.1` (no --skip-nx-cache, NODE_OPTIONS=--max-old-space-size=6144) → ONE PID owns all of 4200/4204/4301; admin styles.css 907,270B + mgmt styles.css 899,109B + both remoteEntry.mjs all HTTP 200 (10/10 & 5/5 stable). Both remotes link external styles.css (not inlined) so 4204/4301 `/styles.css` MUST 200 — a 404/500 there during early build settle is transient, re-probe after 'All remotes started'.
