**Bug:** Changing a user from **Locked → Pending** (the only allowed transition out of Locked per `UserStatusTransitionPolicy.cs:23`) did NOT re-send credentials — the account was unlocked but the user never received a login email, so they could not get back into the first-login flow.

**Root cause** ([CODE] `falcon-core-identity-svc/src/Falcon.Identity.Api/Application/Users/UseCases/ChangeUserStatusProcess.cs`): the `Pending when effectiveStatus == Locked` switch case only called `identityManager.UnlockUserAsync(...)` and set `Status=Pending`. Unlike `CreateUserProcess` (which generates a password, sets it in Zitadel, and publishes `UserCredentialsGeneratedDomainEvent`), the unlock path generated no password and published no credential event.

**First-login flow is status-driven:** `LoginProcess.cs:40,62` sets `isFirstLogin = Status==Pending` and forces `requiresPasswordChange` → routes to `FirstLoginSetupProcess` which sets `Status=Active`. So Pending IS the first-login state; login still needs a known password → must re-issue one.

**Fix (FE/BE = backend-only, identity svc):** in `ChangeUserStatusProcess`, when `NewStatus==Pending`: read tenant `PasswordSecurityLevel` (default Advanced), `passwordPolicy.Generate(level)`, `identityManager.SetPasswordAsync(IdentityUserId, pwd)` BEFORE persisting status (so a provider failure leaves the user safely Locked + retryable), then after persist+cache-clear publish `UserCredentialsGeneratedDomainEvent(Username, pwd, Email, PhoneNumber, FirstName, eDeliveryMethod.Both)`. `Both` guarantees the email (user's complaint) plus SMS parity with creation; the notification handler skips empty channels. Added 3 new ctor deps (`IRepository<TenantSettings>`, `PasswordPolicy`, `IPublisher`) — all already in DI via CreateUserProcess, no DI change.
