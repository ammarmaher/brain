Org-hierarchy **CommChannels & Services / Apps & Services** box (the consolidated `<app-service-pricing>` over the shared `service-pricing-table`). User-reported bug (both consoles): the SA can hide a **paid/Active** service for a client (shouldn't be hideable at all), and **after hide→show the status drops to `InActive` while the wallet balance stays deducted** (customer paid, service lost).

**ROOT CAUSE 🟢 code-verified — concentrated in the shared Commerce domain base `FalconServiceConfigurationBase` (covers apps + comm-channels, both consoles):**
- Bug 1 — `CanHide() => Visibility && Status==InActive` `[CODE] Operations.cs:16-19` does NOT distinguish `InActive (First time)` (never activated, hideable) from post-activation `InActive` (was paid, must NOT be hideable). Discriminator = `FirstActivationDate` (set only in `Activate()` :162, never cleared). So a paid-then-InActive service returns `canHide=true` → SA switch enabled.
- Bug 2 — `SetVisibility()` `[CODE] Operations.cs:122-129` runs `Status = GetInitStatus(Visibility)` UNCONDITIONALLY (show→InActive, hide→None), clobbering committed status. No `PreviousStatus` exists anywhere in Commerce. `SetVisibility` never touches the `Orders` collection or wallet → Paid order + deduction orphaned.

**BRAIN JUDGMENT (answer to "should toggling visibility change status?"): NO — visibility (catalog gate) and lifecycle status are orthogonal.** `BR-AM-14/15` couple visibility→pricing only; `BR-AM-20/23` drive status via payment/activation/renewal. Stopping a paid service = the **Disable** lifecycle action, not catalog Hide. Only `InActive (First time)` (FirstActivationDate==null) is legitimately hideable. **⚠️ `BR-AM-40` (Hide-while-Active) is a formally OPEN PRD rule** `[BRAIN-OUT] prd/modules/01-account-management/BUSINESS_RULES.md:81` — judgment is the safe default but NEEDS business ratification (HALT-AND-FLAG).

**REPAIR = Restore, NOT Refund.** Corruption is accidental (hiding a paid service should never have been allowed) → reinstate status from RenewDate+grace, keep balance. **No refund path exists anywhere** (Charging `OcsWallet` has `ApplyDebit` but no `ApplyCredit`; Commerce `Order` has only Pending/Paid/Failed, no cancel/refund) → refund would be a brand-new cross-service feature, reserved for genuine terminate-and-refund cases. Deduction is auditable+idempotent via `wallet_ledger {refType:"SERVICE_ORDER", refId:orderId}`.

**FIX (Phase 0, HELD per user — not implemented):** `CanHide()` += `&& FirstActivationDate is null`; `SetVisibility` hide-guard `if (!newVisibility && !CanHide()) throw CannotHideServiceWithTheCurrentStatus`. FE switch auto-disables via existing `canHide`+`cannotHideTooltip` — no FE change. Plus xUnit tests + `dotnet build/test`.

**Detection signature:** Tier-1 (`firstActivationDate!=null && status==None(0)`) = unambiguous; Tier-2 (`...&& status==InActive(1) && renewDate>now`) = corruption (Enable can't produce); exclude legit post-grace re-enable (`status==InActive && renewDate<<now`). Join Paid order via `order.mainNodeId==Node._id && order.itemIds∋serviceId && status==2`.
