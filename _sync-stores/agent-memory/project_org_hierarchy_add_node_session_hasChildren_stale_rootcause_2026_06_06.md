**Symptom (live repro 2026-06-06):** acc-owner `cleanowner` on the brand-new clean client `690000000000000000c10009` ("Clean Client", 0 sub-nodes) added an org-hierarchy node ("Test  Node1") via the root kebab → `create-SubNode` returned **200 OK** but the new node never appeared in the tree. User asked for ROOT CAUSE ONLY (no fix).

**Backend is INNOCENT (proven):** `Nodes` doc created + correctly linked — `_id=6a244c5a...`, type 2, level 2, `parentId=ObjectId(690...c10009)`, path `690...c10009.6a244c5a...`. `GET commerce/Node` root now reports `hasChildren:true`; `GET commerce/Node?NodeId=690...c10009` returns the child. Pure FE display bug.

**The recorded "fix" is LIVE but DEFEATED** (served bundle on :4301 contains `queueRootChildSelection`/`pendingAddSelection`/`findChildByName` — confirmed via curl; NOT a stale-bundle problem).

**EXACT ROOT CAUSE — login-cached session node + hasChildren short-circuit:**
1. [CODE] `host-shell/.../organization-hierarchy-tree/services/services.ts:100-136` `getTree()` for a **Client** user does NOT fetch the tree from the backend — it builds the root from `this.sessionProvider.node` (the user's OWN node, loaded ONCE at login by [CODE] `host-shell/core/auth/auth.service.ts:143-153` `fetchOrganizationNode()` → [CODE] `libs/falcon/.../node.service.ts:23` `getNode()` = `GET commerce/Node` → `SessionProvider.setNode`).
2. [CODE] `services.ts:203-214` `orgNodeToFetchNode()` hardcodes **`path: null`** and copies **`hasChildren`** straight from that login snapshot.
3. [CODE] `services.ts:111` **`if (!root.hasChildren) return of(root);`** — when the session node says `hasChildren:false`, getTree returns the root ALONE, **synchronously via `of(root)` (NO HTTP)**, and never calls `getChildren()`. (This is why the post-add network panel shows NO tree refetch.)
4. The session `hasChildren` is **frozen at login**. `cleanowner` logged in while the client had 0 sub-nodes → captured `hasChildren:false`. Adding a node does NOT re-run getNode, so getTree keeps reading `false`.
5. **Both refresh mechanisms are defeated by that one stale root:**
   - Fix path: `node-drawer-state.signals.ts:131-136` (branch `add && targetId===rootId` DOES fire) → `tree-state.signals.ts:330` `queueRootChildSelection` → `refetchTree()` → wrapper `refreshTree()` (`organization-hierarchy-tree.component.ts:465`) → `getTree()` → short-circuits to `of(root)` → no children → `applyTreeUpdate.findChildByName` finds nothing → pending stays queued, tree re-renders root collapsed.
   - Old path: `refreshSelectedPath()` (`tree-state.signals.ts:317`) pushes `selectedNode().path` = **null** → wrapper `startPathRefresh(null)` bails (`organization-hierarchy-tree.component.ts:501`) → no-op.
6. **Only a fresh `getNode()` recovers it** — re-login / token-refresh re-captures the node (now `hasChildren:true`) → getTree then calls `getChildren()` → node appears. This is the tell-tale signature.

**Trigger condition (precise):** any client that had **0 sub-nodes at the moment of login**. The first (and every) node added in that session is invisible until re-login. Ironically the brand-new clean client (the whole point of "no nodes") is exactly what exposes this latent bug — a client that already had ≥1 child at login does NOT hit it (hasChildren:true → getChildren runs → list includes the new node).

**Why the "fix" unit tests gave false confidence:** `tree-state.signals.spec.ts` feeds `applyTreeUpdate` a hand-built tree that ALREADY contains the children + a root with `path:null`; it never exercises the real `getTree()` session short-circuit, so the tests pass while runtime fails.

**✅ FIX APPLIED 2026-06-07 (claude) — at the SOURCE, [CODE] `host-shell/.../organization-hierarchy-tree/services/services.ts:107-120` `getTree()`:** removed the `if (!root.hasChildren) return of(root);` short-circuit so the Client branch ALWAYS fetches the root's live children via `getChildren(root.id)` (= GET commerce/Node?NodeId=root.id, the same call lazy-load uses) instead of trusting the login-frozen `hasChildren`. `map` now also recomputes `hasChildren: children.length > 0` so the root flag stays consistent with its actual children; `catchError(() => of(root))` unchanged (resilient). Net behavior change is SURGICAL: client users now make exactly ONE extra lightweight GET on initial load IFF the root was childless-at-login (returns `[]` → correct empty state) — the exact bug population; clients WITH children at login already called getChildren (no change); Falcon-admin users use the other branch (untouched). This makes the EXISTING refresh machinery work: Add Node → `queueRootChildSelection` → `refetchTree` → `treeRefreshTick` → wrapper `refreshTree()` → `getTree()` → now fetches the new child → `treeChange` → `applyTreeUpdate` → `findChildByName` resolves → node APPEARS (the skeleton renders root.children at level-1 UNCONDITIONALLY — root is implicitly expanded, [CODE] `falcon-tree-panel.component.html:86-110`, no expandedIds gate on the root) AND is SELECTED (page binds `[selectedIdInput]="state.selectedNodeId()"`, [CODE] `org-hierarchy-page-menu.component.html:75`). Did NOT touch `path:null` (changing it would alter the users-list PathPrefix for the root → out-of-scope regression risk) nor add cross-layer session-refresh coupling — the getTree fetch decision was the precise root cause.
