## Wallet page facts (runtime-confirmed)
- **Access is PES `acc.wallet-balance`** (NOT acc-owner-only — that was an FE workaround, now REMOVED). The PES `PolicyRules` store (live, bootstrapped 2026-05-16) provisions it for ALL 3 account roles, per-tenant (`r:{role}@{tenantId}`): **acc-owner** view+transfer+all directions; **acc-admin** view + node-scoped owner→owner transfer (master/channel deny, expr `sourcePath==sub.path`); **acc-user** view+transfer DENY. FIX (2026-05-28, FE-only, build-green): added `managementConsole.wallet.{view,transfer}`→`acc.wallet-balance` to [CODE] falcon-access.registry.ts; route now `shellAccessGuard` + `wallet.view()` ([CODE] wallet-balance-management.routes.ts); Transfer CTA ANDs `wallet.transfer()` PES flag with server `canTransfer` ([CODE] wallet-balance-management.component.ts). Result: acc-owner+acc-admin land, acc-user denied. GOTCHA: PES `/pes/authorize/resources` user subject is `u:{userId}@{tenant}` (NOT `user:{login}@{tenant}`) — probing with the wrong subject returns all-deny (a probe artifact, not policy truth); verify policy via the `PolicyRules` Mongo store, not ad-hoc endpoint probes.
- **walletSettings gates balances**: gateway calls Charging ONLY when `!CanSave`, and `CanSave = (walletSettings is null)` [CODE] GetAccountHierarchyEndpoint.cs:91 + GetAccountHierarchyHandler.cs:60,98. No walletSettings ⇒ canSave=true ⇒ Charging skipped ⇒ all balances 0. walletSettings doc is keyed by **TenantId** (ownerId==tenantId).
- **node-tree balance mapping**: [CODE] AccountHierarchyMapper.cs:232 matches Charging owner-wallet `OwnerId == commerceNode.NodeId`; line 242 `Disabled = ownerNodeWallet is null`; line 236 row id = walletId (fallback nodeId). ## FE dev-server operational recipe (NX Module Federation, 2026-05-28)
To test the mgmt UI: serve TWO processes from `falcon-web-platform-ui` — `npm run serve:management:fast` (management-console remote :4301) AND `npm run start:fast` (host-shell :4200). host-shell loads the remote via `apps/host-shell/src/assets/module-federation.manifest.json` (remoteEntry `http://localhost:4301/remoteEntry.mjs`, active:true). GOTCHAS hit + solved:
- **Dev-servers bind IPv6 `localhost` (`::1`), NOT `127.0.0.1`** — `curl -4 localhost:PORT` returns 000 (false-negative); use plain `curl localhost:PORT` or `[::1]`. The browser's `localhost` resolves to ::1 so it works.
- **NX MF `nx serve` exits code 1 with "Port NNNN is already in use" right after "server ready"** — the orchestrator self-conflicts (its dev-server binds the port, then a second check sees it "in use") BUT the webpack-dev-server CHILD keeps serving the compiled bundle (Windows doesn't kill children on parent exit). So an "exit 1" serve can still be fully functional — verify with `curl localhost:PORT/main.js` (200 + MBs) rather than trusting the exit code. Caveat: orphaned child = no reliable HMR; restart via the npm scripts if code changes need to reload.
- **Clear stale serve zombies first**: `Get-CimInstance Win32_Process -Filter "Name='node.exe'" | ? CommandLine -match 'run-executor' | % { Stop-Process $_.ProcessId -Force }` then confirm ports free (`Get-NetTCPConnection -LocalPort 4200,4301`). Stale half-dead dev-servers from prior sessions are a known phantom-bug source (see [[project_admin_to_mgmt_e2e_verified_2026_05_28]] B-15).
- **CROSS-KILL via npm pre-hooks (the big one)**: `start:fast` AND `serve:management:fast` both run `prestart`/`preserve` = `mf:manifest:dev && ensure:libs`. `mf:manifest:dev` REWRITES `apps/host-shell/src/assets/module-federation.manifest.json` (host-shell watches it) and `ensure:libs` can touch shared-lib dist (management-console watches it). So starting/restarting EITHER server via its npm script triggers a watch-rebuild in the OTHER, which (with the orphaned-child fragility) kills it — a ping-pong (saw mgmt die exit 127, then host-shell die, alternately). FIX: run the pre-hooks ONCE, then start the SECOND server with a DIRECT `npx nx serve <app> --configuration=development` (NO npm pre-hook) so it doesn't rewrite the first's watched files. Recipe that worked: (1) `npm run serve:management:fast` (mgmt :4301, runs hooks once), wait remoteEntry=200; (2) `npx nx serve host-shell --configuration=development` (direct, no hooks), wait :4200/main.js=200 — mgmt survives. Verify with `curl localhost:4200/main.js` + `curl localhost:4301/remoteEntry.mjs` (both 200). Once both up, DON'T re-run the `:fast` scripts (they'll cross-kill); just leave them running.
