**Org Hierarchy: routed user-details + URL-as-state (2026-06-08, claude, FE-only, NO commits).**

User report: on the Organization Hierarchy page, edit a user (change name/username) → Back → the users LIST shows stale values / doesn't re-call the API. User asked for the *best-practice* fix so navigating to any page always (re)loads its APIs for the current selection. Chosen approach = ROUTING (URL-as-state) + structural reload.

- NEW `components/node-workspace/node-workspace.component.ts|.html` = the ENTIRE former `@else` workspace (tabs + view-toggle + node-details header + every tab body incl. users data-table + the 2 Stencil prop-patch effects). **LOAD-BEARING CORRECTNESS INSIGHT (the part a naive routing impl gets WRONG):** `UsersStateSlice` is PAGE-scoped (provided on the parent route) so it SURVIVES the `<router-outlet>` swap. A same-node Back (BMW→user→BMW) does NOT change `effectiveNodeId`, so the `combineLatest([effectiveNodeId, effectiveNodePath, effectiveNodeTenantId, pageNumber, pageSize, refreshTick]) → switchMap(getUsers)` chain would NOT re-fire → list stays stale. FIX = **`NodeWorkspaceComponent` constructor calls `this.state.reloadUsers()` on EVERY mount** (bumps `refreshTick`). Remount = guaranteed refetch. This replaces the stale `(saved)` event chain with a structural guarantee.

**SELECTION ⇄ URL:** node carried as `?node=<id>` QUERY PARAM (chosen over a `:nodeId` path segment to avoid a brittle async default-node redirect + MF segment collisions; trivially switchable later). Tree-click NAVIGATES (`router.navigate([], {queryParams:{node}, queryParamsHandling:'merge'})`) → a `queryParamMap` sub + `(treeReady)` both call `reconcileSelectionFromUrl()` → `applyTreeSelection`. Cold deep-link on a deep LAZY node not yet loaded falls back to default selection (lazy-tree-path-reconstruction = deferred Wave 4, per locked scope "in-session sync first").

**SINGLE unsaved-changes gate (exactly one popup per leave):** child `orgUserDetailsCanDeactivate` (in `org-hierarchy-page.can-deactivate.guard.ts`) delegates to the same `confirmDiscardIfDirty()`; fires on Back / tree-click-to-other-node / sidebar nav. On the user route, tree-click JUST navigates (drops `user/:userId`) — does NOT also call the gate (workspace surfaces info-panel/settings are mutually exclusive with being on the user route). **DOUBLE-POPUP DEFECT I FOUND IN REVIEW + FIXED:** the shared `<app-user-details-page>.onBack()` runs its OWN `confirmLeave` gate then emits `(back)` WITHOUT clearing dirt → the wrapper's nav then hit the route CanDeactivate → 2nd popup. Fix = wrapper `onBack()` calls `this.state.setUserInfoDirty(false)` BEFORE navigating (by `(back)` time the user already agreed to leave). Locked with `user-details-route.component.spec.ts`.

**Routing env facts (verified):** host `app.config.ts` uses `provideRouter(appRoutes, withDisabledInitialNavigation())` — NO `withComponentInputBinding()` (read params via `ActivatedRoute`) + `HashLocationStrategy`. NO custom `RouteReuseStrategy` anywhere (so default destroy-on-navigate holds → the structural-remount guarantee is valid). MF: the admin remote's whole `appRoutes` array is handed to the host router via `loadChildren`, so nested parent+children+outlet is plain Angular (MF boundary sits above).

**BACK-NAV BUG (user's question caught it; my tests had missed it).** User asked "make sure Back from user information reroutes to the org-hierarchy page." The wrapper's `onBack()` used `router.navigate(['../'], {relativeTo: this.route, queryParamsHandling:'preserve'})` — but `user/:userId` is ONE route owning TWO URL segments, and a relative `..` over it is UNRELIABLE: one `..` pops only ONE segment → dead `/…/user` (NG04002 in strict test config, or `**`-redirect to the WRONG default page — admin templates — in the real app); `['..','..']` popped one then APPENDED a literal `..` → `/…/user/..`; `navigate([])` is the "stay, change query only" no-op idiom. **FIX = navigate to the parent shell's ABSOLUTE path built from `this.route.parent.snapshot.pathFromRoot` → `navigate(['/', ...segments], {queryParamsHandling:'preserve'})`** (`navigateToWorkspace()` helper, used by onBack + the no-userId constructor bail). Deterministic, segment-count- AND mount-depth-independent (admin `org-hierarchy-page` vs mgmt `account-administration/…`). Verified by a RouterTestingHarness test that walks to the deepest activated route and drives the REAL relative nav (NOT a hand-typed target URL — that masks the bug, which is exactly the trap the mgmt mirror agent fell into: it copied the buggy `['../']` AND wrote a `navigateByUrl('/?node=')` test that hid it). Applied to BOTH consoles.

**ROUND 4 (2026-06-08) — `pes/authorize/resources` "lost"/cached across target users.** User: opening different users in user-information shows the WRONG (previous user's) permissions/dropdowns because the API is SOMETIMES NOT CALLED; demanded "always call, don't cache — each user has different permissions." **ROOT CAUSE (PRE-EXISTING, not from my edits):** `[CODE] libs/falcon/.../core/lib/access-control/access-control.facade.ts` `ensure()` short-circuits `if (this.store.hasKnownDecision(query)) continue;` — it SKIPS the `pes/authorize/resources` HTTP when a decision is already in the `AccessControlStore`. The store cache is keyed by the QUERY (resource+action+attrs) and reset ONLY on a logged-in-SESSION fingerprint change (`session$` → `reset()`), NOT when the VIEWED TARGET user changes. The 3 user-details authorize resolves (`resolvePermFlags`/`resolveRoleFlags`/`resolveStatusTransitionFlags` in `signals.ts`) now pass `{forceRefresh:true}` → a FRESH `pes/authorize/resources` on every user-info entry. Route/page guards omit the flag → keep caching (unchanged). NOTE the per-entry slice idempotency guards (Round 3) STAY (they cap WITHIN-entry dupes + reset per fetch, so they never caused the cross-user "lost" — that was purely the facade cache); the role CATALOG (`pes/roles`) stays lazy+deduped (Round 3, no force-refresh — it's the options list). ⚠️ DEEPER NUANCE flagged: role/status dropdown queries already vary by the target's role/status (`userRole.other(currentRole,target)` / `userStatus.other(currentStatus,target)`) so different-role targets always re-fetched; but `user.edit(field)` (permFlags) carries NO target attr → if per-target authority must differ for SAME-role users in DIFFERENT NODES, the query needs the target node/path (a PES-query + backend change, separate decision). **GATES: `nx run-many build` host-shell+admin+mgmt GREEN + admin `nx test` 867/47 GREEN + facade spec 18/18 GREEN (+2 new forceRefresh regression tests; `falcon` lib has NO nx test target → ran via `npx vitest run --root libs/falcon`).** PENDING live verify: `pes/authorize/resources` fires on EVERY user-info entry (no longer skipped).

When implementing routed master-detail over a PAGE-scoped data slice, ALWAYS reload-on-mount in the child (the slice survives the outlet swap).
