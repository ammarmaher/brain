Login-connectivity debugging, 2026-05-30. The host-shell login posts to `baseURLIdentityGateway` + `auth/login` ([CODE] auth-api.service.ts `useGateway(Gateway.IdentityGateway)` → `RuntimeBaseUrlInterceptor`). Three causes of "can't log in / connection error", by chosen environment:

**1. QA/staging URLs are BROKEN PLACEHOLDERS (the real "QA connection error").** `apps/host-shell/src/environments/environment.ts` carries 3 URL blocks: prod-remote `*.falconhub.space`, localhost (Docker), staging `*-staging.falconhub.space`. The **staging block is dead**: `auth-staging.falconhub.space` (DNS 8.213.81.122 = the prod ingress) presents a TLS cert for **`CN=core-api.falconhub.space`** (SAN mismatch) → browser **`net::ERR_CERT_COMMON_NAME_INVALID`** + endpoint returns HTTP 503. environment.staging.ts even says "URLs below are placeholders". **WORKING remote = `*.falconhub.space`**: all 5 hosts (auth/core-api/system-api/charging-api/pes-api) have valid matching Let's Encrypt certs; `auth.falconhub.space` CORS already allows `http://localhost:4200` and returns live 401s. FIX = activate the prod-remote block in environment.ts. Browser-verified from localhost:4200: `fetch https://auth.falconhub.space/api/auth/login` → HTTP 401 (connection OK). The `*-staging` hosts need DevOps to deploy a matching cert before reuse. project.json has a correct `staging` build/serve configuration (fileReplacement → environment.staging.ts) — the config mechanism is fine; only the URLs are broken.

**2. localhost (local Docker) — the original ERR_CONNECTION_REFUSED.** Nothing on :7777 because Docker Desktop 4.73.x was crash-looping. Backend log: `initializing Inference manager: ... remove <HOME>\AppData\Local\Docker\run\dockerInference: The file cannot be accessed by the system`. Root = the **Docker Model Runner / "Docker AI"** feature failing on a stale, undeletable `dockerInference` socket; shows dialog "unexpected error…needs to close" [Quit | Reset to factory defaults]. FIX (non-destructive, NOT factory reset): kill Docker Desktop + `wsl --shutdown`; set `EnableDockerAI` → `false` in `%APPDATA%\Docker\settings-store.json` (BOM-free write via `[IO.File]::WriteAllText`); the stale `%LOCALAPPDATA%\Docker\run\dockerInference` resists all delete methods but is harmless once AI is off; relaunch. Then `docker compose up -d` in `C:\Falcon\Falcon\Falcon`. Gotcha: native Windows `MongoDB` service holds 27017 and collides with compose mongo's `27017:27017` → stop it first (needs elevation; set to Manual). Frontend runs locally (ng serve 4200/4204/4301 = node pid); backend = docker (7777/7045/5296 via wslrelay).

**3. local backend, even when up, can't actually log in (2 separate backend bugs).** (a) identity `FieldEncryption:Key` is empty in appsettings ([CODE] AesGcmFieldEncryptor `Convert.FromBase64String`, needs 32-byte base64; Commerce dev key = `caLufAJEpYBleUdRlGJhXP9GjcVGwUCoEiC1l/FqeAE=`) → breaks only the Kafka `UserCreationRequestedConsumer`, NOT login. (b) login throws a non-typed exception in the Zitadel calls `CreateAuthRequestAsync`/`CreateSessionAsync` ([CODE] LoginProcess.cs:37-38, BEFORE password check) → every login (correct or wrong creds) returns generic `"An unknown error occurred"` HTTP 400; sysadmin/accowner exist & are Active in FalconIdentityDb (231 users); Zitadel v4.13.1 API-version-mismatch warnings (lockout policy MethodNotAllowed, webhook sig fail). Use the remote backend to avoid both. Seeded users (pwd Admin@1234): sysadmin/sysops/sysprod (system), accowner/accadmin/accuser (test-tenant-001).

Resolution chosen 2026-05-30: pointed environment.ts at the working remote (`auth.falconhub.space`); 1 FE file changed, NO COMMITS, browser-verified. Relates to [[reference_local_mongo_access_and_listnodeusers_2026_05_30]].

**UPDATE 2026-05-30 (later) — CORRECTED root cause for LOCAL login + Docker AF_UNIX crash-loop recovery.** Point 3(b) above was WRONG: local login does NOT fail because of a Zitadel `CreateSessionAsync` throw. The real cause = **`appsettings.Development.json` is git-UNTRACKED** (commit `862cb44 "untrack appsettings development"` removed it from the identity repo; `git show HEAD:...appsettings.Development.json` → "exists on disk but not in HEAD"). The local copy became a seed-generated **stub** missing `Zitadel:Initialization:WebPlatformRedirectUris` (+ PostLogout). The last fully-tracked version (`git show 862cb44~1:...`) DID contain `WebPlatformRedirectUris: ["http://localhost:4200/auth/callback"]` + `WebPlatformPostLogoutRedirectUris: ["http://localhost:4200/signedout"]`. With redirect URIs empty, `ZitadelAuthService.CreateAuthRequestAsync` (login STEP 1) throws `FalconException(UnknownError)` → HTTP 400 "An unknown error occurred". **FIX = restore those 2 keys** in `appsettings.Development.json` (instance-independent values — always localhost:4200). **OTP disable** = add `"Security": { "OtpRequiredOnLogin": false }` (base `appsettings.json` has it `true`; `LoginProcess.cs`: `otpRequired = isFirstLogin || securityOptions.Value.OtpRequiredOnLogin`; a *Pending* user still gets OTP via isFirstLogin). RUNTIME-VERIFIED local login: `POST localhost:7777/api/auth/login` {sysadmin/Admin@1234} → 200, `result.stage=4` (Authenticated), `requiresOtp=false`, real access+refresh tokens, `Access-Control-Allow-Origin: http://localhost:4200`. The seed (`zitadel-config`/apply-zitadel-config.py) PRESERVES my edits + keeps the same WebPlatformUiClientId across re-up because the zitadel-data volume persists. Backend was NEVER the blocker for local login once redirect URIs present.

**Docker Desktop 4.73 AF_UNIX socket crash-loop (the bigger blocker this session).** Sequence: local Docker **daemon hung** (`docker ps`/`docker version` time out, but containers keep their host port-forwards listening; Zitadel `/debug/ready`=412 because it lost its DB). I FORCE-killed `com.docker.backend` to recover — that left **un-deletable AF_UNIX socket files** (`%LOCALAPPDATA%\Docker\run\dockerInference`, `%LOCALAPPDATA%\docker-secrets-engine\engine.sock`). Every restart, Docker crashes: `initializing Inference manager / Secrets Engine: listening on unix://...: remove ...: The file cannot be accessed by the system. (listener: The filename, directory name, or volume label syntax is incorrect.)` → dialog [Quit | Reset to factory defaults]. **`EnableDockerAI=false` in settings-store.json did NOT stop it** (Secrets Engine is core, not AI). **Deleting the socket file fails** (`Remove-Item`/`[IO.File]::Delete("\\?\..")` both → ERROR_INVALID_NAME); **only `[IO.Directory]::Move(parentDir, bak)` works** (parent-metadata op). Clearing one socket dir only advances the cascade to the next service. **WHAT FIXED IT: `wsl --unregister docker-desktop`** (the factory reset) → on relaunch Docker recreates the distro and the engine starts clean (no crash). **CRITICAL/SURPRISING: this did NOT wipe images/volumes** — all 20 images + every `falcon-*` container + named volumes (mongo-data, zitadel-data, redis-data, minio-data) PERSISTED. So NO rebuild/re-seed was actually needed; `docker compose --project-directory C:\Falcon\Falcon\Falcon -f ...\docker-compose.yml -p falcon up -d core-gateway system-gateway` re-ran the seed chain (zitadel-seed→config, mongo-init, kafka-init, pes-bootstrap all exit 0) and started all backends. **Likely the true root of the wedge = stuck OS-level AF_UNIX state from the force-kill; a Windows reboot would also clear it (less risky than force-killing a hung daemon in the first place).** Stack compose lives at `C:\Falcon\Falcon\Falcon\docker-compose.yml` (project `falcon`); all services use PUBLIC images + `dotnet run` on bind-mounted source (`..:/workspace`), so nothing is locally-built/irreplaceable. Frontend runs as LOCAL `ng serve` on :4200 (separate from the `web-platform-ui` compose container — bring up gateways only to avoid the 4200 collision). Harmless leftovers: `%LOCALAPPDATA%\Docker\run_*_bak*` + `docker-secrets-engine_bak1` (contain the un-deletable sockets; ignore). Seeded users pwd `Admin@1234`: sysadmin/sysops/sysprod + accowner/accadmin/accuser.
