`nx lint admin-console` had ONE error — FIXED 2026-06-06 (claude), branch polishing-v0.4, NO COMMITS.

[CODE] `apps/admin-console/.../contracts-add-wizard/contract-information-step/contract-information-step.component.html:87` — `@angular-eslint/template/label-has-associated-control` ("A label component must be associated with a form element"). The offending element was the **EXTRACTED "Value (SAR)" caption** rendered as a sibling ABOVE the input-number's `.relative` wrapper (the slot-less ﷼/SAR overlay pattern). It was a bare `<label>` with text + a required-`*` span but NO `for` and NO nested control.

**ROOT CAUSE / why `for`/`id` can't fix it:** the `falcon-angular-input-number` wrapper maps its `inputId` @Input onto the Stencil **HOST** `id` attribute (not the inner `<input>`, and not the `input-id` prop) → the inner `<input>` keeps an auto-generated id you can't target. A `for` pointing at a guessed id would dangle (worse a11y than none). So a non-associated `<label>` gives ZERO click-to-focus benefit AND fails the lint rule.

**FIX (task's option 2 — minimal, visually identical):** convert `<label>`→`<span>` (and `</label>`→`</span>`), keeping ALL `falconInputLabelClasses()` token classes + the `[style.color]` error-flip + the nested required-`*` span untouched, so it still matches the sibling date-picker/input-number field labels in the same step. Updated the 3 describing comments for consistency. Did NOT touch any data binding, the input-number element, or the hidden Currency dropdown block (`CreateContractRequest.currency` wire value untouched — that uses `[label]` property binding on `falcon-angular-dropdown`, a component not a native label, so it never triggered the rule).

VERIFIED: `NX_DAEMON=false node node_modules/nx/dist/bin/nx.js lint admin-console --skip-nx-cache` → "All files pass linting" exit 0; `nx build admin-console --configuration=development` → "Successfully ran target build" exit 0.

**LESSON (reusable):** any EXTRACTED caption above a slot-less `falcon-angular-input-number` (the wallet/contracts ﷼ overlay refactors created several) must be a `<span>`, NOT a `<label>` — the wrapper's `inputId`→host-id mapping makes `for` dangle, so `label-has-associated-control` will fire and a real `<label>` buys nothing. Properly-associated labels (e.g. addons-step uses `<label [attr.for]="...">` against real ids) are fine.

## FOLLOW-UP 2026-06-06 (claude) — Value label visually inconsistent + required `*` not red — ROOT-CAUSED + FIXED

User screenshot (live localhost:4200, step-1 Add New Contract): the "Value *" label rendered BIGGER/darker than the sibling "Contract Name/Reference ID/Start Date" labels, and its required `*` was NOT red. **This is independent of the label→span lint fix — it is a token-SCOPE bug, present in both the old `<label>` and the new `<span>`.**

**ROOT CAUSE (gate-12 component-token-scope trap — see [[reference_gate12_component_token_scope_portal_2026_06_02]]):** ALL `--falcon-input-*` tokens — `--falcon-input-label-color` (=neutral-800 #3d3d3d), `--falcon-input-label-font-size` (=xs 12px), `--falcon-input-label-font-weight` (=medium 500), `--falcon-input-label-line-height` (1.3), `--falcon-input-label-color-error`/`--falcon-input-required-color` (=red-500) — are declared ONLY inside `:where(falcon-input, falcon-input-tw, falcon-angular-input, .falcon-input, [data-falcon-input], falcon-password…)` in `libs/falcon-ui-tokens/src/components/input.tokens.css`. The EXTRACTED label is plain markup OUTSIDE that scope, so every `var(--falcon-input-label-*)` / `var(--falcon-input-required-color)` resolved to NOTHING → browser defaults (≈16px, near-black, non-red `*`). (`ms-[length:var(--falcon-spacing-1)]` still worked because `--falcon-spacing-*` is a global `:root` token — only the component-scoped ones broke.) The sibling input/date-picker labels look right because they render INSIDE their component (matching the `:where` selector). `<falcon-input-number>` itself delegates its label to an inner `<falcon-input>` (`falcon-input-number-tw.tsx:524` `label={this.label}`), so the correct contract IS `--falcon-input-label-*`.

**FIX (best-practice, 1 attribute):** add **`data-falcon-input`** to the extracted `<span>`. The token file's `:where()` deliberately lists `.falcon-input, [data-falcon-input]` as the **sanctioned opt-in marker for plain-markup / React/Vue/HTML consumers** (per its own comment) — NOT a hack. The marker sets the `--falcon-input-*` custom props on the span (and the child `*` span inherits `--falcon-input-required-color`), so the already-correct `falconInputLabelClasses()` classes + `[style.color]` error-flip now resolve to the EXACT same values as every other field label → pixel-identical, red `*`, red error-flip, zero future drift. SAFETY-checked: `data-falcon-input` appears ONLY in input.tokens.css (no visual rule) and there is no bare `.falcon-input {}` style rule. Kept it a `<span>` (lint stays green). 1 file, template only, NO binding/Stencil/token change, NO COMMITS.

VERIFIED: lint exit 0 + `nx build admin-console --configuration=development` exit 0. ⚠️ live pixel-verify pending (auth login / credential policy) — user must hard-refresh or rebuild the admin-console remote (dev server showed STALE `<label>`). 

**LESSON 2 (reusable, applies to ALL slot-less extracted form labels in wallet+contracts):** plain markup that consumes `--falcon-input-*` (or ANY component-scoped `--falcon-<comp>-*`) token MUST carry the matching opt-in marker — `data-falcon-input` / `data-falcon-<comp>` (or `.falcon-<comp>` class) — or the vars silently resolve to nothing and you get browser-default text + a non-red required star. Check every extracted ﷼/SAR overlay label (admin+mgmt contracts rate-card/addons/value + wallet) for this same scope gap.
