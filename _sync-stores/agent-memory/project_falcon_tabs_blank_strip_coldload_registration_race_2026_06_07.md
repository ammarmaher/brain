**Symptom (user report 2026-06-07):** In BOTH admin-console and management-console, navigating to a **details page** (reported on Contracts & Cost Mng → contract → Details) sometimes shows the page body WITHOUT the tab strip (Information / Rate Card / Contract Details / Addons). Going Back and re-entering makes it appear; specifically happens on the FIRST navigation right after a build. The user's screenshot was the BUG state — the Information card + "Dates & Value" rendered, but no tab strip above the Mitsubishi header.

**Root cause — Stencil custom-element lazy-registration race (cold load):**
- The strip is `<falcon-angular-tabs>` → renders `<falcon-tabs-tw>` (Light DOM Stencil element), registered ON-DEMAND via `void defineFalconTwComponent('falcon-tabs')` (a dynamic `import()` chunk `falcon-ui-tabs-tw.js`) in the wrapper's `ngOnInit`. `[CODE] libs/falcon-ui-core/src/angular-wrapper/components/falcon-tabs/falcon-tabs.component.ts:69` (pre-fix `void`).
- `[CODE] apps/admin-console/src/main.ts` — the eager `defineCustomElements()` was REMOVED (Wave 5); every wrapper registers its tag lazily → **no warmup list**, so every Stencil wrapper races on a cold load.
- On a COLD load (chunk not yet downloaded — first nav after a build) Angular renders `<falcon-tabs-tw [tabs]="…">` immediately, but the element isn't defined yet. When the chunk loads and the element upgrades, Stencil's connectedCallback re-applies the **default `@Prop() tabs = []`** (`[CODE] libs/falcon-ui-core/src/components/falcon-tabs/falcon-tabs.tsx:53`), clobbering the bound value → `render()` maps over `[]` → ZERO tab buttons paint → blank strip. The page CONTENT still shows because `activeTab` defaults to `'contractInformation'` and the body is a separate `@switch` (not Stencil panel slots) — exactly the screenshot.
- On the SECOND visit the chunk is already loaded → element upgrades synchronously at creation → the declarative `[tabs]` binding sticks → tabs show ("go back and go again").

**Why tabs specifically:** `falcon-stepper`, `falcon-data-table`, and `falcon-dropdown` ALL already fix this race with a deferred imperative push after `componentOnReady()` (stepper template comment: *"Declarative bindings would stringify complex arrays before Stencil hydrates"*; dropdown has elaborate componentOnReady race handling). `falcon-tabs` was the ONE array-prop wrapper that still relied purely on Angular declarative `[tabs]` template bindings → the outlier with the bug.

**FIX (1 file, shared wrapper — fixes EVERY tabs surface in both consoles at once):** `[CODE] falcon-tabs.component.ts` — mirror the stepper pattern: keep the define promise `this.defineReady = defineFalconTwComponent('falcon-tabs')`; add `syncProps()` that awaits `defineReady` then (if present) `el.componentOnReady()` and imperatively assigns `el.tabs/selectedValue/mode/size/orientation/ariaLabel/helperText/errorMessage`; wire `syncProps()` into `ngAfterViewInit` + `ngOnChanges` (guarded on `stencilElRef()`) + `handleChange`. Added `implements OnChanges`, a `FalconTabsLikeElement` cast type, and the `defineReady` field. **KEPT the declarative template bindings untouched** (they drive the working warm-load path every other tabs usage relies on) — lowest-regression; the imperative re-assert only fixes the cold-load case. NO HTML change.

**Verification:** BOTH consoles `nx build …:dev` EXIT 0, each with a fresh `falcon-ui-core` Stencil+wrapper rebuild (NOT cached): management-console Hash `7aa4a9ee4fb8c344`, admin-console Hash `839b168b264b53dc`; `falcon-ui-tabs-tw.js` chunk emitted in both; ZERO new warnings/errors referencing `falcon-tabs.component.ts` (the only build warnings are pre-existing/unrelated: NG8113 unused-imports in templates-details, NG8102 ?? in flow-card/falcon-data-table, tsconfig unused-file notes, Stencil reserved-prop title/scrollHeight on toast/dialog/table). NO commits. ⚠️ Live login click-through pending (credential policy) — but the build IS the user's exact "after I build" repro context, and the fix is the proven codebase pattern (stepper/data-table/dropdown).

**LESSON / cheat-sheet:** Falcon UI Stencil web components register LAZILY per-wrapper (no global warmup). Any `<falcon-angular-*>` wrapper that feeds a COMPLEX ARRAY prop (`tabs`, `steps`, `rows`, `options`, tree data…) purely through Angular declarative `[prop]` bindings will render BLANK/empty on the FIRST cold load after a build, then work on re-nav. Cure = the `defineReady` + `componentOnReady()` deferred imperative `syncProps()` push (see falcon-stepper / falcon-data-table / falcon-dropdown). If you see "X strip/grid empty only on first visit after build", check whether its wrapper has the deferred push. Other array-prop wrappers NOT yet audited for this (potential latent same-bug): multi-select, menu, tree, tree-table, checkbox-group, radio-group, paginator — fix only on report.
