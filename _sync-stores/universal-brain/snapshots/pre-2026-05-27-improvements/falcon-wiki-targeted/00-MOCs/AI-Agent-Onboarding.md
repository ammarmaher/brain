# AI Agent Onboarding

## The architecture in one paragraph

`C:\Falcon\Brain Outputs\` is the **single source of truth** for Falcon's product knowledge. Brain SK **skills** (at `C:\Falcon\Brain SK\skills\`) are the **writers** — only they edit Brain Outputs. The Obsidian vault (`C:\Falcon\falcon-wiki\`) is a **read-only projection** of Brain Outputs, generated by `scan-brain-outputs.ps1`. Every vault note transcludes canonical content from Brain Outputs via `![[_mounts/brain-outputs/...]]`. **The vault is the queryable index — Brain Outputs is the data.**

## Source-of-truth priority (canonical, from Brain SK)

In any conflict, this order wins:

1. **Architecture Wiki** — `_mounts/brain-outputs/wiki-architect/` and `falcon-wiki/Home/Software-Architecture-Design/`
2. **Backend / API truth** — controllers / DTOs / validators / gateway in `_mounts/services/`
3. **PRD** — `_mounts/brain-outputs/prd/modules/` and `10-PRD/`
4. **Existing Angular code** — `_mounts/services/falcon-web-platform-ui/`
5. **Falcon component registry** — `_mounts/brain-sk/registries/FALCON_COMPONENT_REGISTRY.md` and `_mounts/brain-outputs/component-registry/components/<comp>/`
6. **HTML / React visual source** — `_mounts/theme/HTML/` and `_mounts/theme/React/`
7. **Best-practice assumptions** — clearly marked as `[INFERRED]` in your output

**If you state a fact that conflicts between tiers, the lower-numbered tier wins and you must flag the conflict to the user.**

## Step-by-step retrieval contract

### Step 1 — Resolve ambiguous terms via Glossary
"Table" could mean Data Table or Tree Table or HTML `<table>`. Always resolve first via [[Glossary]] before searching.

### Step 2 — Open the projection note for the entity
- Page → `20-Pages/<page>.md`
- Component → `30-Components/<component>.md`
- PRD → `10-PRD/PRD-<module>.md`

The projection note's frontmatter tells you the **canonical Brain Outputs path** at `projection-source:`. The body transcludes the dossier files inline.

### Step 3 — Read the embedded sections, not the projection metadata
The frontmatter is for Dataview queries. The actual knowledge is in the transcluded `![[_mounts/brain-outputs/...]]` blocks below. Read those, not the YAML.

### Step 4 — Follow the SoT priority on every fact
Before stating something, ask: "which tier does this come from?" If the page projection says X, but the Wiki says Y, the Wiki wins. Flag the conflict to the user.

### Step 5 — Confidence-prefix every fact
Every fact in your output must start with one of:

- `[VAULT]` — from a vault MOC or projection frontmatter
- `[BRAIN-OUT]` — from a transcluded Brain Outputs file (most facts will be this)
- `[BRAIN-SK]` — from a Brain SK skill output or registry
- `[MEMORY]` — from agent shared memory
- `[CODE]` — from source code in `_mounts/services/`
- `[WIKI]` — from `_mounts/brain-outputs/wiki-architect/` or `falcon-wiki/Home/`
- `[INFERRED]` — your own reasoning. **Must be flagged so user can sanity-check.**

If you can't find a fact in any of the above, say so. Don't fabricate.

### Step 6 — Verified-at staleness check
Each projection note has `verified-at:` in frontmatter. If older than 90 days, the projection may not reflect current Brain Outputs. Trigger a re-scan: `regenerate vault projections from Brain Outputs`.

## Write-back rule (THE most important)

**Vault projection notes are read-only by convention. Never edit them.** They are regenerated by `scan-brain-outputs.ps1` and your edits will be overwritten.

To change knowledge:
1. Identify which Brain SK skill owns the fact (see table below)
2. Propose invoking that skill to Ammar
3. Skill writes to Brain Outputs (the SoT)
4. Re-run the scanner to refresh the vault projection

| Fact type | Brain SK skill | Writes to |
|---|---|---|
| Page understanding | `business-understanding` + `frontend-master-router` | `Brain Outputs/understanding/pages/<page>/PAGE_OVERVIEW.md` + others |
| Validation rules | `validation-rules` | `understanding/pages/<page>/VALIDATION_RULES.md` |
| PES / authorization | `pes-permission-analysis` | `understanding/pages/<page>/PES_RULES.md` + global matrix |
| Business rules | `business-understanding` | `understanding/pages/<page>/BUSINESS_RULES.md` |
| Component dossier | `component-capability-upgrade` + `frontend-master-router` | `component-registry/components/<comp>/{OVERVIEW,API,USAGE,TOKENS,GAPS_AND_UPGRADES,DECISION}.md` |
| PRD analysis | `business-understanding` (Analyze this PRD) | `prd/modules/<module>/` |
| Visual parity sweep | `screenshot-to-angular` | `understanding/pages/<page>/VISUAL_PARITY_SCORECARD.md` |
| Input → component map | `input-to-component-index` (proposed) | `understanding/frontend/INPUT_CONCEPT_INDEX.md` |
| API / endpoint truth | `backend-api-understanding` | `understanding/backend/` |
| Code conversion | `react-to-angular` / `html-to-angular` | actual Angular code + `understanding/pages/<page>/SOURCE_DESTINATION_COMPARISON.md` |

## Reading order when context is tight

1. The TL;DR callout of the projection note (top of file)
2. The frontmatter (`components:`, `projection-source:`, `verified-at:`)
3. The single transcluded section most relevant to the question (e.g. `COMPONENT_MAPPING` for component lookup, `VALIDATION_RULES` for validation)
4. Glossary entry for any unfamiliar term
